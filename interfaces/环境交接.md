## 一、生产侧与消费侧

环境回答「在哪里、以什么方式执行」，仓库回答「执行什么代码」，两者正交，由任务同时引用。

| 角色 | 谁 | 做什么 |
| --- | --- | --- |
| 生产侧 | 环境生成服务 | 依任务输入生成并固定环境，保存完整定义，提供查询 |
| 消费侧 | 全量检测 | 在环境里执行 clean build 并解析依赖 |
| 消费侧 | 增量检测 | 同一环境下的前后两次检测才可比 |
| 消费侧 | 依赖修复 | 在环境里复构建与复检补丁 |

## 二、约定内容

### 1. 环境是独立对象

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `environment_id` | 是 | 环境的身份，**平台全局唯一**，与 `job_id`、`artifact_id` 同一层级。取代此前提案中的 `configuration_id`——同一环境只有一个名字 |
| `image` | 是 | 引用一条 `IMAGE_REF` 产物（按 `artifact_id`），**不内嵌镜像 tag**：镜像信息只有一处定义 |
| `project_root` | 是 | 代码在**容器内**的位置 |
| `working_directory` | 是 | 从哪个目录执行 |
| `build_command` | 是 | 该环境约定的构建方式。**任务输入不重复传构建命令**，v1 也不支持按任务覆盖 |
| `runtime_capabilities` | 是 | 执行该环境所需的运行能力（v1 只有 `ptrace`）。这是**需求**，不是「当前机器有什么能力」：依赖检测要读文件访问记录，因此检测所用的环境必须声明 `ptrace` |

环境对象没有 `status` 字段。它的生命周期由两条规则表达：**创建后不可变**，以及**改动时新建一个 ID**。
任务有状态机（`QUEUED` → `RUNNING` → 终态），环境没有——把两者混为一谈，会让下游去等一个永远不会出现的
「环境状态变化」。

### 2. 任务只按 ID 引用

1. **任务输入只传 `environment_id`**，不内嵌完整定义，也不传镜像、项目根或构建命令。
2. **完整定义由生产侧保存并提供**，经 `GET /v1/environments/{environment_id}` 取回，响应体即上表结构。
3. **环境创建后不可变**：需要改动时新建一个（`env-001` → `env-002`）。就地修改会让下游手里的同一个 ID 指向两种环境，「按 ID 对齐基线」随即失效。
4. **环境不存在时任务不被受理**：`environment_id` 未登记即 `400`；查询未登记环境返回 `404`。

### 3. 环境生成任务自己的输入

环境生成任务是环境的**产出方**，它的输入不引用 `environment_id`——环境此时还不存在。输入表达的是「生成要求」：仓库、两层成功判据（构建命令与功能验证命令）、执行预算。

| 字段 | 必填 | 校验与语义 |
| --- | --- | --- |
| `repository.url` | 是 | 仓库地址，须可被构建环境克隆 |
| `repository.commit` | 否 | **可缺省、可给缩写**——生成方负责解析：缺省时取默认分支 HEAD，缩写解析为对应提交 |
| `build.command` | 是 | 第一层判据：构建命令，退出码 0 且产物存在 |
| `build.verify_command` | 是 | 第二层判据：功能验证命令 |
| `build.verify_expect` | 否 | 期望输出；缺失时只校验退出码 |
| `build.project_subdir` | 否 | 项目根相对仓库根的路径，默认 `.` |
| `limits.max_iterations` / `.timeout_seconds` | 是 | 执行预算，超限写 `EXEC_4002` |
| `context_documents` | 否 | 供生成时读取的项目文档，最多 2 个 |

字段对应关系是单向的、需要明说的：

| 生成请求里的字段 | 生成结果里的字段 | 注意 |
| --- | --- | --- |
| `build.command` | `Environment.build_command` | 原样成为环境约定 |
| `build.project_subdir` | `Environment.project_root` | **语义不同**：前者是仓库内相对路径，后者是容器内绝对位置。子目录决定容器内的项目根取什么值 |
| `build.verify_command` / `verify_expect` | 不进入环境 | 它们是**本次任务**的成功判据，不是环境属性 |

**校验强度在两侧是不对称的，这是有意设计：**

| 侧 | 接受的 `commit` | 产出/使用的东西 |
| --- | --- | --- |
| 环境生成任务 | 完整 SHA、缩写，或缺省 | 产出 `resolved_commit` 与产物记录的 `source_commit`，**一律是完整 40 位 SHA，且必须是仓库中真实存在的提交** |
| 检测与修复任务 | 只接受完整 40 位 SHA | 按版本逐字符比对（报告、基线、补丁都要落在同一版本上） |

差异来自角色：一方**产出**身份，另一方**消费**身份。要特别说明的是产出一侧的要求——格式合法但仓库中不存在的
SHA 在 schema 上完全合法，却会让下游拿到一条永远对不上的追溯信息，因此生成方必须在产出前解析并确认提交存在。

### 4. 产物归属环境的方式

| 产物 | `environment_id` |
| --- | --- |
| 环境生成服务自己的产物（`DOCKERFILE` / `BUILD_LOG` / `VERIFY_LOG` / `IMAGE_REF`） | 一律为 `null`——产出时环境尚不存在 |
| 其余服务的产物 | 必须记录所属环境，否则下游无法判断它是在哪个环境里产出的 |

存储域**按服务命名**：`draft` / `mdfixer` / `buildchecker` / `echecker`；**人工基线样例**的产物用 `oracle` 域，
以免冒充工具产出。取值集合是契约的一部分，由校验钉死——新增域必须先写进共享结构与文档，否则下游按域
映射本地目录的约定会静默失效。

### 5. 成功输出的不变式

`status = SUCCEEDED` 蕴含：

- `environment_id` 指向一个可查询的环境；
- `image_artifact_id` 与该环境的 `image` 是同一个编号（两处若不一致，同一环境就有了两个名字）；
- `dockerfile_artifact_id`（`DOCKERFILE`）与 `image_artifact_id`（`IMAGE_REF`）都指向登记在案的产物，
  均可经 `GET /v1/artifacts/{artifact_id}` 取回；两条产物记录的 `environment_id` 一律为 `null`。

### 6. 跨主机部署

`image` 指向 `IMAGE_REF` 产物，产物内容即镜像引用。切换到镜像仓库时只改产物内容与取值，**不改结构**。

## 三、可执行的最小检查

在 `main` 分支执行 `python scripts/validate.py`（检查 06、14）：

1. 环境记录符合 `environment.schema.json`；
2. 每个任务样例引用的 `environment_id` 都有对应环境记录；
3. 环境的 `image` 能解析到一条 `IMAGE_REF` 产物，且该产物由环境生成服务产出（`environment_id` 为 `null`，存储域按服务命名）；
4. 环境生成服务的产物记录 `environment_id` 为 `null`，其余产物记录所属环境；
5. 检测所用环境声明了 `ptrace`；
6. 报告所依据的提交等于该环境产出时的提交。

在 `main` 分支运行 `python scripts/mock_server.py` 后可实测：

| 用例 | 期望结果 |
| --- | --- |
| 创建环境生成任务 | `202` → `SUCCEEDED`，输出含 `environment_id` 与 `image_artifact_id` |
| `GET /v1/environments/{environment_id}` | `200`，返回完整环境定义 |
| 用该 `environment_id` 创建检测或修复任务 | `202`，正常受理 |
| 引用未登记的环境 | `400` |
| 查询未登记的环境 | `404` |
| 环境生成任务：`commit` 给 7 位缩写 | `202` → `SUCCEEDED`，`resolved_commit` 为完整 40 位 |
| 环境生成任务：完全不给 `commit` | `202` → `SUCCEEDED`，解析默认分支 HEAD 并回报完整 SHA |
| 环境生成任务：给一个格式合法但仓库中不存在的 SHA | `202` → `FAILED / EXEC_4002`，不产出带假提交的记录 |
