# 契约阶段文档

本仓库用于存放本项目**合作契约阶段**的文档。

## 这个仓库的职责

四个环节——环境生成、全量检测、增量检测、依赖修复——之间要约定清楚接口，并且组合起来能形成一条可联调的流水线。契约阶段的全部文档都放在这里。

**本阶段产出的是文档，不是实现。** 各工具的源码实现不属于本分支的职责范围。

## 目录说明

| 目录 | 存放内容 | 谁维护 |
| --- | --- | --- |
| `shared/` | 第一阶段的共享内容：公共数据结构、任务类型、系统错误与状态 | 第一阶段全体共同维护 |
| `interfaces/` | 接口契约 | 该接口的生产侧与消费侧 |
| `records/` | 工作记录 | 每人一份，各自维护 |

三个目录现在都是空的，各放了一个 `.gitkeep` 占位文件——git 不记录空目录，需要它来占位。放入实际内容后可以删掉。

## 接口契约的工作规则

**一条接口一个文档，单独存放、单独提交。**

- 文件名带接口编号，例如 `interfaces/I1-运行拓扑.md`、`interfaces/I4-错误报告.md`。编号固定，便于排序与相互引用。
- **为什么单独提交**：一条接口谈定就可以独立冻结，不必等其余几条都谈完；提交历史里也能直接看出每条接口各自是怎么演进的。
- 每份接口文档建议包含四部分：生产侧与消费侧、约定内容、可执行的最小检查、双方确认状态。
- **全部接口冻结后，合并成一份文档**，例如 `interfaces/00-接口契约-合并稿.md`。
- 合并稿只在冻结之后产生，不参与讨论——讨论始终发生在各自的接口文档里，这样每条接口的演进过程不会被合并稿覆盖掉。

## 工作记录

**建议每个人单独记录一份文档。**

- 文件名带自己的标识与所负责的环节，例如 `records/A1-BuildChecker.md`、`records/B2-MDFixer.md`。
- 内容自定。建议至少记三类：读了什么、提出了什么问题、得到了什么回答，以及还有什么没解决。
- **为什么每人一份**：一是契约阶段的讨论散落在群聊里，个人记录是唯一能还原「我提过什么、谁回答了什么」的东西；二是六个人往同一份文档里写会不断冲突。

## 与 main 分支的关系

- 本分支 `contract-phase` 是一个**无父提交的空分支**，与 `main` 没有共同历史。
- 原因：`main` 上的内容在本阶段之前独立产出，未经六人共同讨论确认。契约阶段从零开始，避免把已有内容当作既定前提。
- `main` 保留下来作为**参考**：可以查阅、可以引用，但不作为本分支的前提。
- 需要 `main` 上的文件时有两条路：
  - 只看不取：`git show main:<路径>`
  - 取到本分支：`git checkout main -- <路径>`，取过来之后就归本分支管理，可以自由修改
