# 公共数据结构

> **来源**：任务（Job）部分的语义边界由六人讨论确定；产物引用与仓库标识两部分提取自 `main` 并已选定方案
> **状态**：第一、二、三节的方案已定；第四节环境标识为新立结构，待细化
> **阅读方式**：每节先给总览，再给详细边界；未定的事项列在该节末尾

## 本文范围

第一阶段要确认的三类公共信息之一：**各接口共用的数据结构**。

本文有四节：任务（Job）、产物引用（Artifact）、仓库与版本标识（Repository）、环境标识（Environment）。第四节是第二节的 A5 决定带来的——环境不再用产物表示，因此独立成结构。

这里只列"谁都要用"的部分——各接口自己的字段属于第二阶段，不在本文。

## 一、任务（Job）

### 快速总览

四类任务共用同一套外层结构，分五组。

| 组 | 字段 | 一句话边界 |
| --- | --- | --- |
| **Identity** | `schema_version`、`job_id`、`trace_id` | 回答"这是什么、属于哪次流程"；创建后不可变 |
| **Lifecycle** | `status`、`job_type` | 回答"任务进行到哪一步"；不表达结果好坏 |
| **Execution** | `created_at`、`started_at`、`finished_at`、`attempt` | 任务级的时间与尝试次数，以服务端时钟为准 |
| **input** | 由 `job_type` 决定 | 调用方提交并经服务接受的输入快照，创建后不可变 |
| **result** | `output`、`error` | 终态结果，成功产出与失败原因互斥 |

### 1. Identity

**总览**：三个字段共同回答"这是什么、属于哪次流程"。全部在 Job 创建后不可变。

**详细边界**

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `schema_version` | 是 | **Job Schema 的契约版本**，声明"读这份数据要按哪一版规则解析"。**覆盖公共外壳与四类任务各自的 `input` / `output` 形状——任何一处形状变化都要递增。** 它不是任何具体服务的实现版本，服务升级而数据结构未变时不动它。 |
| `job_id` | 是 | **一次任务实例**的编号，**平台级全局唯一**。由服务端产生，创建请求中不得携带。重试与新一轮都不会复用同一个 `job_id`。 |
| `trace_id` | 否 | **一次业务流程的串联号，覆盖多轮反馈循环**。从提交仓库到补丁验证通过之间的所有 Job 共享同一个 `trace_id`。它不承载业务含义、不参与任何判定，只用于串联。由调用方透传，缺失时服务端生成。 |

`trace_id` 是唯一能跨越多个 `job_id` 的串联键。原因是失败的任务无法重试（见 `attempt` 一节），要再跑一次只能提交新 Job。

`schema_version` 的覆盖范围是公共外壳加四类任务的专有结构，即消费方只需要盯一个版本号。代价是粒度较粗——某一类接口改了形状，全部消费方都要跟着升级。将来若认为过粗，再讨论拆分；届时需要新增字段来承载分接口的版本。

### 2. Lifecycle

**总览**：两个字段回答"任务进行到哪一步"。一个是会演进的当前进展，一个是不可变的种类。

**详细边界**

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `status` | 是 | 任务自身的执行状态。取值穷举，未知取值必须被拒绝。只能由拥有该任务的服务修改。 |
| `job_type` | 是 | 任务种类，决定 `input` 与 `output` 的具体结构。创建后不可变，且必须与创建端点一致。 |

生命周期回答"任务进行到哪一步"，**不回答"结果好不好"**。检出问题仍然是成功完成。

**状态机**：

```
QUEUED ──► RUNNING ──► 任意终态
   │
   └───────────────► CANCELLED

终态：SUCCEEDED / FAILED / TIMED_OUT / CANCELLED
```

- `QUEUED` 只能到 `RUNNING` 或 `CANCELLED`；
- `RUNNING` 可以到任意终态；
- **终态不可再次转换**；
- 取消由**调用方**发起，取消后仍可查询。

### 3. Execution

**总览**：三个时间字段加一个计数，描述**任务级**的时间与尝试次数。全部以服务端时钟为准。

**详细边界**

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `created_at` | 是 | 服务**成功创建 Job 资源并持久化之后**的服务端时间。不是调用方发起请求的时刻。 |
| `started_at` | 否 | 该 Job **第一次**开始执行的时间。不随重试更新。 |
| `finished_at` | 否 | 该 Job **最终进入终态**时的服务端时间。 |
| `attempt` | 是 | 最终完成前**实际执行的尝试次数**。尚未开始执行时为 `0`；首次进入执行时变为 `1`，每次重新执行递增 1。全程是整数，不存在"没有值"的情形。 |

三个时间字段在 Job 对象中**始终存在**，尚未发生的取 `null`——是取空值，不是省略字段。

**统一的时间格式**：RFC 3339 / ISO 8601，**UTC**，**毫秒精度**。

**`started_at` 的"第一次"决定了读数含义。** `finished_at − started_at` 是整个任务的总耗时，**含全部重试**。单次尝试花了多久，从这三个时间字段里算不出来——这是边界，不是缺口；将来若确实需要，属于另一套结构。

**`attempt` 是最容易"同名不同义"的一处**：

- 只计**同一个 `job_id` 上被重新执行**；
- 任务内部的迭代**不计入**——换一版 Dockerfile、试一个候选补丁这类，由 `input` 里的轮数上限约束；
- 重试时状态**保持在 `RUNNING`，不回 `QUEUED`**；
- 不表达成功与否，只表达"这是第几次"；
- **未执行时取 `0` 而不是 `null`**：`null` 留给"尚未发生的时刻"，而 `attempt` 是一个计数——没有执行过就是 0 次，这样它全程是整数，统计口径不会分叉。

**不变式**：

| 不变式 | 说明 |
| --- | --- |
| `created_at ≤ started_at ≤ finished_at` | 三者非 null 时成立 |
| `status = QUEUED` ⟹ `started_at`、`finished_at` 均为 `null`，且 `attempt = 0` | 尚未开始 |
| `status = RUNNING` ⟹ `started_at` 非 null 且 `finished_at` 为 `null` | 执行中 |
| `status` 为终态 ⟺ `finished_at` 非 null | 终态必有结束时间 |
| `started_at` 非 null ⟺ `attempt ≥ 1` | 执行过才计次 |
| 终态且 `started_at` 为 `null` ⟹ `status = CANCELLED` | 从未执行就被取消，是合法状态 |

### 4. input

**总览**：调用方提交的输入快照，创建后不可变。

**详细边界**

表示调用方创建 Job 时提交、并经服务接受的输入参数。Job 创建后不可修改，不因重试、内部迭代或执行过程发生变化。具体字段结构由 `job_type` 对应的接口契约定义。

### 5. result

**总览**：终态结果的统称，由 `output` 与 `error` 两个并列字段承载，两者互斥。

**详细边界**

| 字段 | 语义边界 |
| --- | --- |
| `output` | 成功产出。**可以包含"发现了问题"**——检出缺失依赖属于成功产出，不是失败。 |
| `error` | 系统执行错误。只写"判断没做成"类的故障，不写业务发现。 |

- 两者**只在终态出现**，`QUEUED` / `RUNNING` 阶段不出现；
- `SUCCEEDED` ⟹ 必有 `output`，且不得同时有 `error`；
- `FAILED` / `TIMED_OUT` / `CANCELLED` ⟹ 必有 `error`；
- 不装大对象内容，大对象走产物引用。

**实际生效值与 `input` 的关系**：服务在执行过程中可能对输入做默认填充、规范化或约束调整。**此类实际生效值不得覆盖 `input`。** 若该变化对任务执行语义或结果解释具有重要影响，由具体接口契约定义相应的 `effective_config` 或等价字段。

## 二、产物引用（Artifact）

### 快速总览

产物引用解决的是一件事：**大文件不进任务响应，以"记录 + 地址"交接**。一条产物记录由六组信息组成。

| 组 | 字段 | 一句话边界 |
| --- | --- | --- |
| **身份** | `artifact_id` | 平台内唯一的产物编号 |
| **类型** | `type` | 八类之一，决定内容是什么 |
| **地址** | `uri`、`media_type` | 到哪里取、取回来是什么格式 |
| **来源** | `producer_job_id` | 哪个任务产出的 |
| **校验** | `sha256`、`size_bytes` | 取回来的内容是否完整 |
| **追溯** | `created_at`、`source_commit` | 什么时候、基于哪个源码版本产出的 |

产物类型共八类：

`DOCKERFILE`、`BUILD_LOG`、`VERIFY_LOG`、`IMAGE_REF`、`ACTUAL_GRAPH`、`DECLARED_GRAPH`、`ERROR_REPORT`、`PATCH`

### 详细边界

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `artifact_id` | 是 | 平台内全局唯一的产物编号。 |
| `type` | 是 | 产物类型，八类之一。类型与产出方的绑定**允许一个类型有多个合法产出方**。 |
| `uri` | 是 | 形如 `artifact://<存储域>/<job_id>/<文件名>`。存储域**按服务命名**，用于定位到产出该产物的服务。 |
| `media_type` | 是 | 取回来是什么格式。 |
| `producer_job_id` | 是 | 哪个任务产出的，用于追溯。 |
| `sha256` | 是 | **一律必填**：任何产物都要给内容摘要，下游可无条件核验。 |
| `size_bytes` | 是 | 与 `sha256` 同属校验组；摘要既已必填，体积也已确定。 |
| `created_at` | 否 | 产物产出的时间。 |
| `source_commit` | 条件必填 | **当产物能对应到某个源码版本时必填**，否则不填。是否"能对应"由产出方在产出时判断；消费方不能假设它一定存在。 |

**存放与取用**

- 产物**分散存放**：各服务各自存放自己产出的产物；
- 存储域**按服务命名**，例如 `artifact://draft/<job_id>/<文件名>`、`artifact://echecker/<job_id>/<文件名>`；
- 取用一律走**下载接口** `GET /v1/artifacts/{artifact_id}`。

**已记录的取舍**：产物记录**不承载"产出前提"**（不含构建配置标识与生成者版本）。因此"两份产物是否在相同前提下产出"无法只从产物记录判断。这一信息需要由具体接口在各自的结构里表达，或经由环境标识关联——见第四节。

### 本节待细化

1. **类型与产出方的对应表**——哪些类型允许多个产出方，哪些只允许一个。
2. **分散存放下的产物定位**——分散存放加统一下载接口，下载接口必须知道产物在哪个域。可选做法是按 URI 的存储域转发到对应服务，或维护一张全局产物索引。
3. **`size_bytes` 与 `created_at` 的必填性**未单独讨论，当前按"`size_bytes` 必填、`created_at` 可选"记录。

## 三、仓库与版本标识（Repository）

### 快速总览

仓库与版本标识解决的是一件事：**说明"是哪个仓库的哪个版本"**。它是每条接口都要引用的基础对象。

| 字段 | 一句话边界 |
| --- | --- |
| `url` | 调用方给出的仓库地址，原样保存 |
| `canonical_url` | 归一化后的地址，用于判断"是不是同一个仓库" |
| `commit` | 版本标识，完整 SHA |

### 详细边界

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `url` | 是 | 仓库地址，**原样保存**调用方给出的写法。 |
| `canonical_url` | 是 | 归一化后的地址，**用于比对**——判断两条记录指的是不是同一个仓库。 |
| `commit` | 是 | **完整 40 位 SHA**。不接受缩写、分支名、标签。 |

**只支持 git。** 字段因此就叫 `commit`，不引入更泛的版本控制概念。

**项目根路径不在本节。** 仓库根不一定是构建根（可构建的项目可能在子目录里），该路径归环境标识——见第四节。

**不表达工作副本状态。** 契约假定工作副本是干净的；基于被改过的代码产出的结果，无法从本结构识别。

由于只接受完整 SHA，不存在"请求值与实际生效值不一致"的情形，因此这一维度上不需要 `effective_config`。

### 本节待细化

1. **归一化的具体规则**——至少覆盖 `.git` 后缀、大小写、主机名写法。
2. **`canonical_url` 的字段名**——当前是暂用名。

## 四、环境标识（Environment）

### 快速总览

环境标识解决的是一件事：**说明"在什么环境里执行的"**。

本节由两个决定产生：A5 决定环境不再用产物表示、独立成结构；R4 决定项目根路径归环境标识。

### 详细边界

已知必然包含的内容：

| 内容 | 为什么在它里面 |
| --- | --- |
| 镜像引用 | 起容器用，是环境的载体 |
| 构建配置标识 | 环境的身份由版本与配置共同确定，缺配置则两次结果不可比 |
| 项目根路径（容器内） | R4 定它归环境 |
| 运行约定：工作目录、构建命令、是否需要跟踪能力等 | 这些是下游起容器时必须知道的信息 |

### 本节待细化

1. **字段名与结构形态**。
2. **运行约定的具体内容**——工作目录、构建命令、验证命令、是否需要跟踪能力，逐项确定。
3. **是否包含仓库标识**——即环境是否引用第三节的 Repository。
4. **与 `IMAGE_REF` 产物类型的重叠**——八类产物类型里有 `IMAGE_REF`，而环境已独立成结构，需要决定该类型是保留还是移除。
