# 公共数据结构

> **来源**：任务（Job）部分的语义边界由六人讨论确定；产物引用与仓库标识两部分提取自 `main` 并已选定方案
> **状态**：四节的模型都已确定；第四节另有两处待确认（见该节待细化）
> **阅读方式**：每节先给总览，再给详细边界；未定的事项列在该节末尾

## 本文范围

第一阶段要确认的三类公共信息之一：**各接口共用的数据结构**。

本文有四节：任务（Job）、产物引用（Artifact）、仓库与版本标识（Repository）、环境标识（Environment）。第四节是第二节的 A5 决定带来的——环境不再用产物表示，因此独立成结构。

四个结构各自回答一个问题，边界互不重叠：

| 结构 | 回答的问题 |
| --- | --- |
| 任务（Job） | 做什么动作 |
| 产物引用（Artifact） | 产出了什么 |
| 仓库与版本标识（Repository） | 执行什么代码 |
| 环境标识（Environment） | 在哪里、以什么方式执行 |

这里只列"谁都要用"的部分——各接口自己的字段属于第二阶段，不在本文。

## 一、任务（Job）

### 快速总览

四类任务共用同一套外层结构，分五组。

| 组 | 字段 | 一句话边界 |
| --- | --- | --- |
| **Identity** | `schema_version`、`job_id`、`trace_id` | 回答"这是什么、属于哪次流程"；创建后不可变 |
| **Lifecycle** | `status`、`job_type` | 回答"任务进行到哪一步"；不表达结果好坏 |
| **Execution** | `created_at`、`started_at`、`finished_at`、`attempt` | 任务级的时间与尝试次数，以服务端时钟为准 |
| **input** | 由 `job_type` 决定 | 调用方提交并经服务接受的输入快照，创建后不可变 |
| **result** | `output`、`error` | 终态结果，成功产出与失败原因互斥 |

### 1. Identity

**总览**：三个字段共同回答"这是什么、属于哪次流程"。全部在 Job 创建后不可变。

**详细边界**

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `schema_version` | 是 | **Job Schema 的契约版本**，声明"读这份数据要按哪一版规则解析"。**覆盖公共外壳与四类任务各自的 `input` / `output` 形状——任何一处形状变化都要递增。** 它不是任何具体服务的实现版本，服务升级而数据结构未变时不动它。 |
| `job_id` | 是 | **一次任务实例**的编号，**平台级全局唯一**。由服务端产生，创建请求中不得携带。重试与新一轮都不会复用同一个 `job_id`。 |
| `trace_id` | 否 | **一次业务流程的串联号，覆盖多轮反馈循环**。从提交仓库到补丁验证通过之间的所有 Job 共享同一个 `trace_id`。它不承载业务含义、不参与任何判定，只用于串联。由调用方透传，缺失时服务端生成。 |

`trace_id` 是唯一能跨越多个 `job_id` 的串联键。原因是失败的任务无法重试（见 `attempt` 一节），要再跑一次只能提交新 Job。

`schema_version` 的覆盖范围是公共外壳加四类任务的专有结构，即消费方只需要盯一个版本号。代价是粒度较粗——某一类接口改了形状，全部消费方都要跟着升级。将来若认为过粗，再讨论拆分；届时需要新增字段来承载分接口的版本。

### 2. Lifecycle

**总览**：两个字段回答"任务进行到哪一步"。一个是会演进的当前进展，一个是不可变的种类。

**详细边界**

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `status` | 是 | 任务自身的执行状态。取值穷举，未知取值必须被拒绝。只能由拥有该任务的服务修改。 |
| `job_type` | 是 | 任务种类，决定 `input` 与 `output` 的具体结构。创建后不可变，且必须与创建端点一致。 |

生命周期回答"任务进行到哪一步"，**不回答"结果好不好"**。检出问题仍然是成功完成。

**状态机**：

```
QUEUED ──► RUNNING ──► 任意终态
   │
   └───────────────► CANCELLED

终态：SUCCEEDED / FAILED / TIMED_OUT / CANCELLED
```

- `QUEUED` 只能到 `RUNNING` 或 `CANCELLED`；
- `RUNNING` 可以到任意终态；
- **终态不可再次转换**；
- 取消由**调用方**发起，取消后仍可查询。

### 3. Execution

**总览**：三个时间字段加一个计数，描述**任务级**的时间与尝试次数。全部以服务端时钟为准。

**详细边界**

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `created_at` | 是 | 服务**成功创建 Job 资源并持久化之后**的服务端时间。不是调用方发起请求的时刻。 |
| `started_at` | 否 | 该 Job **第一次**开始执行的时间。不随重试更新。 |
| `finished_at` | 否 | 该 Job **最终进入终态**时的服务端时间。 |
| `attempt` | 是 | 最终完成前**实际执行的尝试次数**。尚未开始执行时为 `0`；首次进入执行时变为 `1`，每次重新执行递增 1。全程是整数，不存在"没有值"的情形。 |

三个时间字段在 Job 对象中**始终存在**，尚未发生的取 `null`——是取空值，不是省略字段。

**统一的时间格式**：RFC 3339 / ISO 8601，**UTC**，**毫秒精度**。

**`started_at` 的"第一次"决定了读数含义。** `finished_at − started_at` 是整个任务的总耗时，**含全部重试**。单次尝试花了多久，从这三个时间字段里算不出来——这是边界，不是缺口；将来若确实需要，属于另一套结构。

**`attempt` 是最容易"同名不同义"的一处**：

- 只计**同一个 `job_id` 上被重新执行**；
- 任务内部的迭代**不计入**——换一版 Dockerfile、试一个候选补丁这类，由 `input` 里的轮数上限约束；
- 重试时状态**保持在 `RUNNING`，不回 `QUEUED`**；
- 不表达成功与否，只表达"这是第几次"；
- **未执行时取 `0` 而不是 `null`**：`null` 留给"尚未发生的时刻"，而 `attempt` 是一个计数——没有执行过就是 0 次，这样它全程是整数，统计口径不会分叉。

**不变式**：

| 不变式 | 说明 |
| --- | --- |
| `created_at ≤ started_at ≤ finished_at` | 三者非 null 时成立 |
| `status = QUEUED` ⟹ `started_at`、`finished_at` 均为 `null`，且 `attempt = 0` | 尚未开始 |
| `status = RUNNING` ⟹ `started_at` 非 null 且 `finished_at` 为 `null` | 执行中 |
| `status` 为终态 ⟺ `finished_at` 非 null | 终态必有结束时间 |
| `started_at` 非 null ⟺ `attempt ≥ 1` | 执行过才计次 |
| 终态且 `started_at` 为 `null` ⟹ `status = CANCELLED` | 从未执行就被取消，是合法状态 |

### 4. input

**总览**：调用方提交的输入快照，创建后不可变。

**详细边界**

表示调用方创建 Job 时提交、并经服务接受的输入参数。Job 创建后不可修改，不因重试、内部迭代或执行过程发生变化。具体字段结构由 `job_type` 对应的接口契约定义。

### 5. result

**总览**：终态结果的统称，由 `output` 与 `error` 两个并列字段承载，两者互斥。

**详细边界**

| 字段 | 语义边界 |
| --- | --- |
| `output` | 成功产出。**可以包含"发现了问题"**——检出缺失依赖属于成功产出，不是失败。 |
| `error` | 系统执行错误。只写"判断没做成"类的故障，不写业务发现。 |

- 两者**只在终态出现**，`QUEUED` / `RUNNING` 阶段不出现；
- `SUCCEEDED` ⟹ 必有 `output`，且不得同时有 `error`；
- `FAILED` / `TIMED_OUT` / `CANCELLED` ⟹ 必有 `error`；
- 不装大对象内容，大对象走产物引用。

**实际生效值与 `input` 的关系**：服务在执行过程中可能对输入做默认填充、规范化或约束调整。**此类实际生效值不得覆盖 `input`。** 若该变化对任务执行语义或结果解释具有重要影响，由具体接口契约定义相应的 `effective_config` 或等价字段。

## 二、产物引用（Artifact）

### 快速总览

产物引用解决的是一件事：**大文件不进任务响应，以"记录 + 地址"交接**。一条产物记录由六组信息组成。

| 组 | 字段 | 一句话边界 |
| --- | --- | --- |
| **身份** | `artifact_id` | 平台内唯一的产物编号 |
| **类型** | `type` | 八类之一，决定内容是什么 |
| **地址** | `uri`、`media_type` | 到哪里取、取回来是什么格式 |
| **来源** | `producer_job_id` | 哪个任务产出的 |
| **校验** | `sha256`、`size_bytes` | 取回来的内容是否完整 |
| **追溯** | `created_at`、`source_commit` | 何时可被引用、针对哪个代码版本 |

产物类型共八类：

`DOCKERFILE`、`BUILD_LOG`、`VERIFY_LOG`、`IMAGE_REF`、`ACTUAL_GRAPH`、`DECLARED_GRAPH`、`ERROR_REPORT`、`PATCH`

### 详细边界

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `artifact_id` | 是 | 全局唯一 Artifact 身份。 |
| `type` | 是 | 业务类型，八类之一。 |
| `uri` | 是 | **稳定逻辑 URI**，形如 `artifact://<存储域>/<job_id>/<文件名>`。它是逻辑地址，不表示物理位置——落到实际位置由取用方式负责。存储域按服务命名。 |
| `media_type` | 是 | 内容／表示格式。 |
| `producer_job_id` | 是 | **唯一**的具体产出 Job。每条记录只有一个产出任务，即使该类型允许多个产出方。 |
| `created_at` | 是 | Artifact **成功持久化并可引用**的时间。与 Job 的 `created_at` 用同一条定义。 |
| `sha256` | 是 | 对 **Artifact 的实际内容**计算 SHA-256，用于内容完整性校验。 |
| `size_bytes` | 否 | Artifact 内容大小，不适用时为空。 |
| `source_commit` | 是 | 产物所针对的代码版本。**当前八类产物一律必填**——每一类都能对应到一次具体的代码版本执行。 |

本节"必填"一栏的"否"表示**字段始终存在、值在不适用时为空**，不是"可以省略字段"——与第一节时间字段的约定一致。

**`sha256` 哈希的是产物内容，不是镜像摘要。** 以 `IMAGE_REF` 为例，它的内容是 `{"image": "registry.example.com/project@sha256:abc..."}` 这样一段记录——`Artifact.sha256` 哈希的是**这段记录本身**；而 `sha256:abc...` 是 Docker 镜像在镜像仓库里的不可变身份。两者作用不同，不要混用。

**`source_commit` 为什么八类都能必填**：

| `type` | `source_commit` | 为什么能必填 |
| --- | --- | --- |
| `DOCKERFILE` | 必填 | DRAFT 为指定代码版本生成构建环境 |
| `BUILD_LOG` | 必填 | 当前四个服务产生的构建日志，均对应一次具体代码版本上的执行 |
| `VERIFY_LOG` | 必填 | 当前定义中的验证均针对具体代码版本 |
| `IMAGE_REF` | 必填 | 环境是针对指定 commit 构建出来的 |
| `ACTUAL_GRAPH` | 必填 | 依赖图对应具体 commit |
| `DECLARED_GRAPH` | 必填 | 声明依赖图对应具体 commit |
| `ERROR_REPORT` | 必填 | 全量／增量检测结果对应具体 commit |
| `PATCH` | 必填 | 补丁的修改基线就是具体的 source commit |

这张表是"一律必填"的依据：每一类产物都能说清它对应哪次代码版本。若将来出现无法对应到具体提交的产物类型，需要单独讨论例外，而不是默认省略。

**类型与产出方**

| `type` | DRAFT | BuildChecker | EChecker | MDFixer | 说明 |
| --- | :---: | :---: | :---: | :---: | --- |
| `DOCKERFILE` | 是 | — | — | — | 环境构建定义 |
| `BUILD_LOG` | 是 | 是 | 按实际执行 | 按实际执行 | 构建／执行日志，多产出方 |
| `VERIFY_LOG` | 是 | 是 | — | 是 | 实际执行验证时产出 |
| `IMAGE_REF` | 是 | — | — | — | 镜像引用产物，被环境引用 |
| `ACTUAL_GRAPH` | — | 是 | — | — | 全量实际依赖图 |
| `DECLARED_GRAPH` | — | 是 | — | — | 全量声明依赖图 |
| `ERROR_REPORT` | — | 是 | 是 | — | 全量／增量检测均可产出 |
| `PATCH` | — | — | — | 是 | 修复产物 |

- **"按实际执行"**表示**不是必须产出**：该服务执行了对应操作并形成持久化日志时可以产出；没有执行对应验证的服务，不需要为了满足规则强行生成空日志。
- 绑定关系是约束：产出方不在允许列表内的产出应被拒绝。
- 每条产物记录的 `producer_job_id` 只有一个，即使该类型允许多个产出方。

**验证结论与验证日志的分工。** 结构化的验证结论留在 `output`（是否通过、判据是什么），详细的执行日志放 `VERIFY_LOG`。只有结论、没有日志，失败细节就留在服务内部，跨服务定位与审计会失去依据。

**存放与取用**

- 产物**分散存放**：各服务各自存放自己产出的产物；
- 存储域**按服务命名**，例如 `artifact://draft/<job_id>/<文件名>`、`artifact://echecker/<job_id>/<文件名>`；
- 取用一律走**下载接口** `GET /v1/artifacts/{artifact_id}`。
- **定位机制**：逻辑上采用**全局 Artifact Index** 的思路——`artifact_id` 在全平台唯一，并可据此定位到产物的存放位置。**实现上不要求部署一个独立的 Index 服务**；按存储域转发、各服务自维护目录、或一个中心服务，都属实现选择。

**已记录的取舍**：产物记录**不承载"产出前提"**（不含构建配置标识与生成者版本）。因此"两份产物是否在相同前提下产出"无法只从产物记录判断。这一信息需要由具体接口在各自的结构里表达，或经由环境标识关联——见第四节。

## 三、仓库与版本标识（Repository）

### 快速总览

仓库与版本标识解决的是一件事：**说明"是哪个仓库的哪个版本"**。它是每条接口都要引用的基础对象。

| 字段 | 一句话边界 |
| --- | --- |
| `url` | 调用方给出的仓库地址，原样保存 |
| `canonical_url` | 按平台统一规则生成的规范地址，用于地址的比较与关联 |
| `commit` | 版本标识，完整 SHA |

### 详细边界

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `url` | 是 | 仓库地址，**原样保存**调用方给出的写法。 |
| `canonical_url` | 是 | 按平台统一规则生成的规范地址，**用于仓库地址的比较与关联**。 |
| `commit` | 是 | **完整 40 位 SHA**。不接受缩写、分支名、标签。 |

**`canonical_url` 不是仓库的唯一身份。** 它只解决"同一个地址的不同写法"，不能解决"不同地址实际指向同一个仓库"——例如源站与镜像站同步着同一个仓库，两者的 `canonical_url` 并不相同。所以它的用途限定为**规范化与等价比较**，不保证识别不同 URL 是否指向同一个 Git 仓库。

```
两个仓库地址
      ↓
 canonicalization
      ↓
 比较 canonical_url
      ↓
 是否指向同一个规范地址
```

**只支持 git。** 字段因此就叫 `commit`，不引入更泛的版本控制概念。

**项目根路径不在本节。** 仓库根不一定是构建根（可构建的项目可能在子目录里），该路径归环境标识——见第四节。

**不表达工作副本状态。** 契约假定工作副本是干净的；基于被改过的代码产出的结果，无法从本结构识别。

由于只接受完整 SHA，不存在"请求值与实际生效值不一致"的情形，因此这一维度上不需要 `effective_config`。

本节的完整形态：

```json
{
  "url": "https://github.com/241880199/DevOps.git",
  "canonical_url": "https://github.com/241880199/DevOps",
  "commit": "b06e66eecf58c74ce6f17067f36a9a3ad17af244"
}
```

### 归一化规则

| 项目 | 规则 | 示例 |
| --- | --- | --- |
| 协议 | 接受 `https://`、`http://`、`ssh://` 与 SCP 形式（`git@host:path`）；比较时统一为 HTTPS 形式 | `git@github.com:x/y.git` → `https://github.com/x/y` |
| 主机名大小写 | **转小写** | `GitHub.COM` → `github.com` |
| 路径大小写 | **不转换** | `/User/Repo` 与 `/user/repo` 视为不同 |
| `.git` 后缀 | 去除 | `/x/y.git` → `/x/y` |
| 末尾 `/` | 去除 | `/x/y/` → `/x/y` |
| 默认端口 | 去除 `:443` 与 `:80` | `https://github.com:443/x/y` → `https://github.com/x/y` |
| fragment | **禁止** | `#foo` 不属于仓库身份 |
| query | **禁止** | `?ref=main` 不作为仓库身份 |
| 用户名与密码 | **禁止** | 不允许出现在仓库地址里 |
| host 别名 | **不自动推断** | `github.com` 与 `github.enterprise.local` 视为不同 |
| 路径中的重复 `/` | **不压缩** | 避免改变合法路径的含义 |

**不要把整个 URL 转小写。** DNS 主机名不区分大小写，但 URL 的路径部分不能由平台假定大小写不敏感。规则是：**hostname 转小写，path 保持原样**。

**SSH 的边界。** 从 SSH 形式转换到 HTTPS 形式，只对 Git hosting 的标准地址形式成立，不能声称任意 SSH 地址都能安全转换。若想进一步降低实现与测试成本，v1 也可以收缩为"只接受 HTTPS Git 地址"。

### 归一化只有一处实现

**不要让四个服务各自实现归一化。** 各自写一份必然出现细微差异——一个去掉了末尾 `/`、一个没有、一个补上了 `https://` 前缀——最后四个服务对同一个仓库得出不同的 `canonical_url`，比对静默失效：

```
DRAFT        github.com/x/y.git → https://github.com/x/y
EChecker     github.com/x/y.git → https://github.com/x/y/
MDFixer      github.com/x/y.git → github.com/x/y
```

因此归一化规则属于**第一阶段的公共语义**，而不只是某个接口的字段定义：一处产出结果、其余服务消费，或至少四个服务共用同一份规则实现。

这条规则的**实现归属**（共享库、公共组件，还是由某个服务提供接口）需要在接口阶段确定——否则会出现"规则人人同意、实现没人负责"。

### 本节待细化

无，本节已收口。

## 四、环境标识（Environment）

### 快速总览

环境**不是产物，而是一个独立的业务对象**：它由一条镜像引用加上一组运行约定组成，回答"在什么环境里执行的"。

边界一句话：**`IMAGE_REF` 只是环境的一个组件。** 镜像引用只回答"用哪个镜像"，而下游还需要知道代码放在哪、从哪个目录执行、执行什么命令、有没有跟踪能力。

它与仓库的关系是**正交**的：仓库回答"执行什么代码"，环境回答"在哪里、以什么方式执行"。同一个代码版本可以在不同环境里执行，一个通用构建环境也可以服务多个仓库。

### 详细边界

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `environment_id` | 是 | 环境的身份，**平台全局唯一**——与 `job_id`、`artifact_id` 同一层级。下游直接拿它引用环境。 |
| `image` | 是 | **引用一条 `IMAGE_REF` 产物**（按 `artifact_id` 引用），不内嵌镜像信息。 |
| `project_root` | 是 | 代码在容器内的位置。 |
| `working_directory` | 是 | 从哪个目录执行。 |
| `build_command` | 是 | 该环境约定的构建方式。 |
| `runtime_capabilities` | 是 | **执行该环境所需的运行能力**——是需求，不是"当前机器有什么能力"。 |

**环境一旦创建即不可变。** 需要改动时不修改已有环境，而是新建一个：`env-001` 改动后成为 `env-002`。这条是基线可比性的前提——环境若可以变，两份依赖图是否可比就无从判断。

**`runtime_capabilities` 采用结构化声明，但 v1 只冻结实际被依赖的能力**，当前只有 `ptrace`。结构化便于将来扩展（例如 `network`、`gpu`），但不预先定义用不到的能力。

### 环境与任务的分工

```
Job
├── repository   url + commit   ← 执行什么代码
└── environment_id              ← 在哪里、以什么方式执行
        │
        └── Environment
              ├── image ──► IMAGE_REF Artifact
              ├── project_root
              ├── working_directory
              ├── build_command
              └── runtime_capabilities
```

**环境不内嵌仓库身份。** 仓库与环境保持正交：同一个 commit 可以在不同环境执行，一个通用构建环境也可以服务多个仓库。由 Job 同时引用两者，而不是让环境强绑定某个仓库。

**环境不内嵌进任务输入，而是用 `environment_id` 引用。** 环境是可复用的执行上下文——一个环境可以同时服务全量检测、增量检测与修复。若每次都把完整环境内嵌进 `input`，既冗余，也让"多个任务用的是不是同一个环境"无从判断。

**构建命令只在环境里表达。** 环境定义"这个项目在这个环境下应该怎么构建"，任务定义"我要对这个环境做什么"。任务输入**不重复传构建命令**——两处都有值，冲突时无从判断哪个为准。**v1 不支持按任务覆盖构建命令**：覆盖会立刻带来"这还算不算同一个环境"的问题，除非检测方明确提出需求。

### 引用方式

下游任务通过 `environment_id` 引用环境，完整定义由 Environment Provider（当前是 DRAFT）保存并提供，下游按需解析。

### 本节待细化

1. **产物如何关联到环境。** 环境 ID 是基线可复现性的关键锚点，而产物记录不承载"产出前提"（第二节的取舍）。两条合起来的问题是：**"这份基线图是在哪个环境产出的"无法从图谱记录本身判断。** 一条不需要给产物加字段的路子是经 `producer_job_id` 反查产出该产物的任务，再读该任务的 `environment_id`——链是通的，但依赖两个条件：产出方的任务输入里有 `environment_id`，且 Job 记录可长期查询。
2. **`configuration_id` 是否还单独存在。** 环境不可变且全局唯一之后，"两次结果是否可比"只需比较 `environment_id`；原先"环境身份由版本与配置共同确定"的 `configuration_id` 角色已被它吸收，是否从契约里移除需要确认。
