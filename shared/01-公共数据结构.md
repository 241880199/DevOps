# 公共数据结构

> **来源**：提取自 `main` 分支（`contracts/task.schema.json`、`contracts/artifact.schema.json`）
> **状态**：讨论起点，未经六人确认。文末「待确认」是本阶段需要定下来的部分。

## 本文范围

第一阶段要确认的三类公共信息之一：**各接口共用的数据结构**。

这里只列"谁都要用"的部分——各接口自己的字段属于第二阶段，不在本文。

---

## 一、任务（Job）

四类任务共用同一套外层结构，公共字段对四类任务完全一致。

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `schema_version` | ✅ | 契约版本，形如 `1.0`。改字段语义时必须递增 |
| `job_id` | ✅ | 任务编号，服务端产生，形如 `job-xxx`。**创建请求中不得携带** |
| `job_type` | ✅ | 任务类型，四选一（见 `02-任务类型.md`） |
| `status` | ✅ | 任务状态（见 `03-系统错误与状态.md`） |
| `trace_id` | ⬜ | 串联同一次流程的追踪号，由调用方透传 |
| `execution` | ⬜ | 执行元数据：`created_at` / `started_at` / `finished_at` / `attempt` |
| `input` | ⬜ | 任务输入，具体结构由 `job_type` 决定 |
| `output` | ⬜ | 任务产出，**仅在终态出现**，具体结构由 `job_type` 决定 |
| `error` | ⬜ | 系统执行错误，结构见下表 |

`error` 的结构：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `code` | ✅ | 错误码，形如 `ENV_3002` |
| `message` | ✅ | 人类可读的错误摘要 |
| `stage` | ⬜ | `ENV` / `EXEC` / `ANALYSIS` / `REPAIR` |
| `detail` | ⬜ | 补充说明，例如容器内命令与退出码 |
| `at` | ⬜ | 时间 |

---

## 二、产物引用（Artifact）

大文件不进任务响应，一律以"产物记录 + URI"交接。

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `artifact_id` | ✅ | 产物编号，平台内全局唯一 |
| `type` | ✅ | 产物类型，八选一 |
| `uri` | ✅ | 产物地址，形如 `artifact://<存储域>/<job_id>/<文件名>` |
| `media_type` | ✅ | MIME 类型 |
| `producer_job_id` | ✅ | 产出该产物的任务，用于追溯 |
| `sha256` | ⬜ | 内容摘要，交接时核验完整性 |
| `size_bytes` | ⬜ | 字节数 |
| `created_at` | ⬜ | 产出时间 |
| `source_commit` | ⬜ | 产出时仓库所处的 commit |

产物类型共八类：

`DOCKERFILE`、`BUILD_LOG`、`VERIFY_LOG`、`IMAGE_REF`、`ACTUAL_GRAPH`、`DECLARED_GRAPH`、`ERROR_REPORT`、`PATCH`

---

## 三、仓库与版本标识（Repository）

每条接口都要说明"是哪个仓库的哪个版本"。

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `url` | ✅ | 仓库地址 |
| `commit` | ✅ | commit SHA |

## 待确认

1. **`commit` 的取值形式。** main 的文字要求是"完整 SHA"，但取值约束实际允许 7 位缩写——缩写无法唯一绑定到具体提交，正是这个字段要防的事。
2. **产物 URI 的存储域。** main 里出现了三种写法（`b03` / `detect` / 按任务类型命名）。消费方要按存储域去取文件，不统一取不到。
3. **产物记录的必填划分。** `sha256` 与 `source_commit` 目前都是可选，但"可追溯"这件事完全建立在它们之上。
4. **是否需要新增字段。** 例如检测器版本——修复的验收依赖"用同一版本复检"，而现有结构里没有承载它的位置。
