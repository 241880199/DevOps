## 第一轮：环境交接 —— A 组要什么，B 组交什么

**A 组的需求（依 `job-input-full-check.schema.json` 反推）**

| 需要什么 | 为什么 |
| --- | --- |
| 仓库地址 + **完整** commit SHA | 基线必须绑定到具体提交，不接受分支名或标签 |
| 可运行镜像 `image_ref` | 在其中执行 clean build |
| **`configuration_id`** | 与 commit 共同确定基线身份；缺了，两次检测结果不可比 |
| clean build 命令、项目根目录 | 检测器要在容器里跑完整构建 |

**B 组的交接（依 `job-output-draft.schema.json`）**

| 交出什么 | 对应字段 | 状态 |
| --- | --- | --- |
| 可运行镜像 | `output.image_ref` | ✅ 已有 |
| 实际使用的版本 | `output.resolved_commit` | ✅ 已有 |
| Dockerfile 原文 | `output.dockerfile_artifact_id` → 产物 | ✅ 已有 |
| 迭代记录 | `output.iterations[]` | ✅ 已有 |
| **构建配置标识** | `output.configuration_id` | ⚠️ **本轮新增，见 ADR-007** |

**本轮发现的两个缺口（均由 B 组在本轮补上）**

1. **`configuration_id` 没有生产者。** A 组要在输入里填它，却只能自己发明；而环境是 B 组造的。两个小组各起一个名字，跨任务比较会在「看起来都正常」的情况下失效。
   → 提案见 `docs/ADR/ADR-007-DRAFT输出的构建配置标识.md`。**请 A 组确认：这个标识由 DRAFT 回报是否可接受？取值粒度按「凡影响依赖关系的都算在内」是否够用？**

2. **DRAFT 无法指定项目子目录。** 请求样例里写着 `repository.url` + `commit` + `command: make`，但本仓库根目录并没有可构建的 `make` 目标——样例项目在 `fixtures/draft/`。不补这个字段，DRAFT 只会在仓库根跑 `make`，然后以「构建不通过」收场，而真实原因只是找错了目录。
   → 已新增可选字段 `build.project_subdir`，样例已改为 `"fixtures/draft"`。

**A03 确认结果**

- ✅ 接受由 DRAFT 回报 `configuration_id`（ADR-007）
- ✅ E2 联调确认在同机使用本地 `image_ref`（`draft-fixture-ok:1.0`）；跨主机时再改用镜像仓库地址
- ✅ E2 不要求额外交付构建产物本身（可执行文件、`.o`）

## 第二轮：报告交接 —— B 组要什么，A 组交什么

**B 组的需求（依 `contracts/job-input-repair.schema.json` 与 ADR-005）**

| 需要什么 | 为什么 |
| --- | --- |
| 报告 URI + `artifact_id` | 修复的目标来源 |
| `finding_type: MISSING` | 修复只针对缺失依赖，请求修冗余依赖会被拒绝 |
| **报告所依据的 commit** | 报告属于哪个源码版本，是补丁能否应用的前提 |
| 每条发现的 `location` + `evidence` | 光有 `(target, dependency)` 无法复核：不知道去哪一行确认、凭什么这么说 |
| `provenance` 区分工具与人工 | 人工标准答案不能混进工具准确率统计 |

**A 组的交接（依 `contracts/error-report.schema.json`）**

| 交出什么 | 状态 |
| --- | --- |
| `schema_version` / `repository` / `produced_by` / `generated_at` / `findings` | ✅ 契约已定 |
| 每条发现必填 `location` + `evidence` | ✅ 契约已定 |
| `provenance` 三类枚举（`TOOL` / `INSTRUCTOR_ORACLE` / `MANUAL`） | ✅ 契约已定 |
| 报告可同时含 `MISSING` 与 `REDUNDANT` | ✅ 契约已定，边界在请求侧收窄 |

**本轮发现的一个缺口（B 组本轮补上）**

3. **报告版本无法在受理阶段校验。** 契约写着「报告必须与请求的 `repository.commit` 一致，否则报告失效」，但请求只给报告的 URI——服务端必须先取回报告才知道版本对不对。不符时已经白跑了一次调度。
   → `report` 新增**可选** `commit`：填了就在受理阶段比对，不符直接 `400` 拒绝；不填则退回执行阶段校验。**请 A 组确认是否愿意在请求侧带上这个值。**

**B 组提供的实物，供 A 组对照**

| 文件 | 用途 |
| --- | --- |
| `fixtures/mdfixer/error-report.json` | 固定人工报告（`INSTRUCTOR_ORACLE`），每条发现都指向磁盘上真实存在的行 |
| `fixtures/mdfixer/` | 报告所指的真实源码项目（含参考补丁与参考镜像） |
| `contracts/samples/error-report.json` | 契约样例，演示 `MISSING` / `REDUNDANT` 与两种来源并存 |

> **请 A 组用 `fixtures/mdfixer/` 核对一件事**：报告说「`Makefile` 第 9 行的 `main.o` 规则缺 `config.h` / `feature.h`，且多声明了 `unused.h`」——打开文件数一下，是不是这样。这正是我们要求每条发现都带 `location` 与 `evidence` 的目的：**位置写出来了，就该能被数一遍**。

**A03 确认结果**

- ✅ 接受可选字段 `report.commit`
- ✅ 接受增量检测的 `baseline.commit` 与 `base_commit` 一致性检查；不一致时在受理阶段返回 `400`
- ✅ 接受 `configuration_id` 粒度：凡影响依赖关系的配置变化都必须产生不同标识

## 第三轮：加入一个失败输入 —— 状态与错误码怎么定

**讨论对象**：修复任务的失败边界。

### 争议点：「所有候选都被拒绝」算不算失败？

两种说法都说得通，不写死就会出现两套实现：

| 立场 | 理由 |
| --- | --- |
| 判 `SUCCEEDED` | 修复服务正常完成了工作——在给定输入下确实没有可接受的补丁。这是结论，不是故障 |
| 判 `FAILED` | 这次修复没产出任何补丁，等于没做成 |

### B 组的决定（已写入 ADR-006）

判 **`SUCCEEDED`**。决定性理由不是状态语义，而是**信息放在哪里**：

> `FAILED` 的任务没有 `output`。若把「全部候选被拒」判为 `FAILED`，`rejected[]` 里逐候选的理由就无处安放——而那是修复服务唯一有价值的产出。

由此得到两条不变式，已被 `scripts/validate.py` 检查 08 强制：

- `output.fixed` 非空 ⟹ `verification` 三项均为 `true`；
- `output.fixed` 为空 ⟹ `output.rejected` 非空，且不带 `patch_artifact_id`。

### 错误码

原 `contracts/error-codes.md` 的编码规则写着「阶段取 `ENV` / `EXEC` / `ANALYSIS` / `REPAIR`」，分段表却只有 `3xxx` / `4xxx` / `5xxx`——**`REPAIR` 阶段没有任何码**。本轮补上 `6xxx` 修复段：

| 错误码 | 含义 | 与 `rejected[]` 的区别 |
| --- | --- | --- |
| `REPAIR_6001` | 修复输入不可用：报告取不到 / 不符合契约 / 版本与请求不符 | 判断**没做成**——输入不可信 |
| `REPAIR_6002` | 修复过程无法进行：缺补丁工具、工作副本不可写 | 判断**没做成**——工具跑不起来 |

`rejected[]` 是**做完判断**的结果：候选被正常评估过，只是结论为「不可接受」。

### 失败输入样例

`contracts/samples/job.failed.repair6001.json`：请求的 `repository.commit` 与报告所依据的版本不一致，且请求未声明 `report.commit`，因此到执行阶段取回报告后才发现。任务 `FAILED`，`error.code = REPAIR_6001`。

**请 A 组用同一套判据检查自己那边**：`ANALYSIS_5001`（分析器崩溃）是判断没做成；「检出 MD/RD」是做完判断。两者若混同，调度器会把成功的分析当故障重跑。

**A03 确认结果**

- ✅ 接受「全部候选被拒 → `SUCCEEDED` + `fixed: []` + `rejected` 非空」
- ✅ 接受 `6xxx` 由 B 组修复阶段使用，A 组分析类错误码使用 `5xxx`
- ✅ 确认检出问题不等于执行失败（E2 检查项 04）

## A03 回复（2026-09-21）

A03 接受以下提案，并以新增契约和样例作为可执行回复：

- DRAFT 在输出中回报 `configuration_id`，检测服务原样沿用。凡影响依赖关系的编译选项变化都必须产生不同标识。
- 修复请求接受可选 `report.commit`，填写时在受理阶段核对版本。
- `baseline.commit` 必须等于 `base_commit`，`baseline.configuration_id` 必须等于本次环境配置；不一致在受理阶段拒绝。
- 检出 MD/RD 表示检测成功完成，任务状态为 `SUCCEEDED`；分析器未完成工作才使用 `ANALYSIS_5001`。
- `FULL_CHECK` 输出实际图、声明图和错误报告；`INCREMENTAL_CHECK` 额外输出新增/消除发现和更新后的实际图。

## A03 补充回复（2026-09-23）

A03 对此前仍未明确答复的事项补充确认如下：

- **产物读取方式**：选择 `GET /v1/artifacts/{artifact_id}`。任务输出先给出 artifact ID，接收方下载原始字节后按产物记录中的 `sha256` 和 `size_bytes` 核验；不依赖双方服务共享本地目录。
- **镜像交付位置**：E2 联调在同一台主机执行，接受本地 `image_ref`。若后续改为跨主机执行，再把该字段切换为双方可访问的镜像仓库地址；这不改变字段结构。
- **构建产物本身**：E2 不要求 B03 额外交付可执行文件或 `.o`。BuildChecker/EChecker 在所交付镜像内执行约定的构建命令并自行产生临时构建文件。
- **修复无可用补丁的终态**：接受“全部候选被拒仍为 `SUCCEEDED`，`fixed: []` 且 `rejected` 非空”；这是修复服务完成判断后的正常结论。
- **错误码分段**：接受 B03 的修复错误使用 `6xxx`，A03 的分析错误使用 `5xxx`；检出 MD/RD 不属于分析器失败。

A03 检测产物通过 `contracts/samples/artifact.*-00*.json` 给出可下载记录，对应实物位于 `fixtures/a03/`。这些文件是人工契约样例，不冒充 BuildChecker/EChecker 的真实运行输出。
