# 增量依赖检测

- **端点**：`POST /v1/incremental-check-jobs`
- **`job_type`**：`INCREMENTAL_CHECK`
- **状态**：提案，待双方确认后冻结

## 一、生产侧与消费侧

| 角色 | 谁 | 做什么 |
| --- | --- | --- |
| 生产侧 | 增量检测（EChecker） | 不做完整重建，按提交增量推断依赖变化 |
| 消费侧 | 依赖修复 | 取回错误报告，作为待修复问题的来源 |
| 消费侧 | 维护者 | 取回变化集，看这一轮新增与消除了哪些依赖问题 |
| 消费侧 | 平台任务入口 | 按 `job_id` 查询任务结果 |

**复检沿用本接口**，不另立任务类型：修复产出补丁后要验证，走的就是一次增量检测。

## 二、约定内容

### 1. 创建请求

在全量检测的输入之外增加四项：

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `base_commit` | 是 | 基线的完整 40 位 SHA |
| `baseline.actual_graph_artifact_id` | 是 | 基线实际图的全局产物编号，由全量检测产出 |
| `baseline.commit` | 是 | 应**等于** `base_commit`，不一致时任务被拒绝 |
| `baseline.environment_id` | 是 | 应与本次的 `environment_id` 一致，不一致时结果不可比 |

`repository` 与 `environment_id` 的要求与全量检测相同。

**受理阶段的两条比对**（不满足即 `400`）：

```
baseline.commit          == base_commit
baseline.environment_id  == environment_id
```

### 2. 成功输出

| 字段 | 语义边界 |
| --- | --- |
| `base_commit` | 本次比较的基线版本，回显以便下游串起两轮 |
| `resolved_commit` | 实际检测的完整 40 位 SHA |
| `environment_id` | 本次检测所处的环境 |
| `error_report_artifact_id` | 依赖问题报告（`ERROR_REPORT`）的全局产物编号 |
| `changes.added[]` / `changes.resolved[]` | 本轮新增与消除的发现，元素与报告里的发现同构 |

**本接口不产出 `ACTUAL_GRAPH`。** 按共享产出方矩阵，`ACTUAL_GRAPH` 只由全量检测产出；增量这一轮的变化用 `changes` 表达，而不是交出一张新图。

### 3. 错误边界

与全量检测一致：检出 MD / RD 时终态仍是 `SUCCEEDED`；分析器没跑完才用 `FAILED / ANALYSIS_5001`。

## 三、可执行的最小检查

| 用例 | 期望结果 |
| --- | --- |
| 有效增量检测请求 | `202` → `SUCCEEDED`，输出报告编号与变化集 |
| 删除 `baseline` | `400` |
| `baseline.commit` 不等于 `base_commit` | `400` |
| `baseline.environment_id` 不等于本次 `environment_id` | `400` |
| 检出 MD / RD | `SUCCEEDED` |

## 四、双方确认状态

| 项 | 状态 |
| --- | --- |
| 依赖检测侧 | 已采用（见 `docs/ADR/ADR-009`、`ADR-010`） |
| 环境生成与依赖修复侧 | 待确认 |

待确认（本接口最需要拍板的一条）：

**增量检测不产出 `ACTUAL_GRAPH`，是否满足后续多轮增量算法？** 若某一轮增量结束后需要一张更新过的实际图作为下一轮的基线，就必须修改共享产出方矩阵，再同步 Schema——不能由本地实现单方面例外。当前口径是「一轮基线 + 逐轮 `changes`」。
