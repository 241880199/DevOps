# 查询环境定义

- **端点**：`GET /v1/environments/{environment_id}`
- **适用**：全部四类任务的下游
- **状态**：提案，待双方确认后冻结

## 一、生产侧与消费侧

| 角色 | 谁 | 做什么 |
| --- | --- | --- |
| 生产侧 | 环境生成服务 | 保存环境完整定义，提供查询 |
| 消费侧 | 全量检测、增量检测 | 取回镜像、项目根、构建命令与运行能力，据此起容器 |
| 消费侧 | 依赖修复 | 取回复构建与复检所需的环境约定 |
| 消费侧 | 维护者 | 核对某个环境到底固定了什么 |

任务是环境的**引用方**，只传 `environment_id`，不内嵌完整定义。

## 二、约定内容

### 1. 返回体

```json
{
  "environment_id": "env-draft-fixture-mode0",
  "image": "image-ref-001",
  "project_root": "/workspace/fixtures/draft",
  "working_directory": "/workspace/fixtures/draft",
  "build_command": "make",
  "runtime_capabilities": ["ptrace"]
}
```

| 字段 | 语义边界 |
| --- | --- |
| `environment_id` | 平台全局唯一的环境身份，与 `job_id`、`artifact_id` 同一层级。取代此前的 `configuration_id`——同一环境不再有两个名字 |
| `image` | 引用一条 `IMAGE_REF` 产物（按 `artifact_id`），**不内嵌镜像 tag**：镜像信息只有一处定义 |
| `project_root` | 代码在**容器内**的位置 |
| `working_directory` | 从哪个目录执行 |
| `build_command` | 该环境约定的构建方式。**任务输入不重复传构建命令**，v1 也不支持按任务覆盖 |
| `runtime_capabilities` | 执行该环境所需的运行能力（v1 只有 `ptrace`）。这是**需求**，不是「当前机器有什么能力」——依赖检测要读文件访问记录，因此检测所用环境必须声明 `ptrace` |

### 2. 四条约定

1. **环境创建后不可变**：需要改动就新建一个（`env-001` → `env-002`）。就地修改会让下游手里的同一个 ID 指向两种环境，「按 ID 对齐基线」随即失效。
2. **任务不内嵌环境定义**：检测与修复只传 `environment_id`；内嵌 `image_ref` / `build_command` / `project_subdir` 都会被拒绝。
3. **环境不存在时任务不被受理**：`environment_id` 未登记即 `400`；查询未登记环境返回 `404`。
4. **环境没有 `status` 字段**：它的生命周期由上面第 1 条表达。任务有状态机，环境没有——把两者混为一谈，会让下游去等一个永远不会出现的「环境状态变化」。

### 3. 跨主机部署

`image` 指向 `IMAGE_REF` 产物，产物内容即镜像引用。切换到镜像仓库时只改产物内容与取值，**不改结构**。

## 三、可执行的最小检查

运行 `python scripts/mock_server.py` 后实测：

| 用例 | 期望结果 |
| --- | --- |
| 查询已登记的环境 | `200`，返回上表六个字段 |
| 查询未登记的环境 | `404` |
| 检测任务引用未登记的环境 | `400` |
| 检测任务引用未声明 `ptrace` 的环境 | `400` |
| 环境的 `image` 能解析到一条 `IMAGE_REF` 产物 | 该产物由环境生成服务产出，`environment_id` 为 `null` |
