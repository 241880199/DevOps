# 生成构建环境

- **端点**：`POST /v1/dockerfile-jobs`
- **`job_type`**：`DRAFT`
- **状态**：双方已确认并冻结；实现与样例齐备

## 一、生产侧与消费侧

| 角色 | 谁 | 做什么 |
| --- | --- | --- |
| 生产侧 | 环境生成服务 | 依输入生成并固定环境，保存完整定义，提供查询（见 `查询环境定义.md`） |
| 消费侧 | 全量检测 | 在环境里执行 clean build 并解析依赖 |
| 消费侧 | 增量检测 | 同一环境下的前后两次检测才可比 |
| 消费侧 | 依赖修复 | 在环境里复构建与复检补丁 |
| 消费侧 | 维护者 | 重建、审查或复现环境时取 Dockerfile 与镜像产物 |

这是四类任务中**唯一不引用环境**的一类——它是环境的产出方，输入表达的是「生成要求」。其余三类任务的输入都必须引用已存在的环境。

## 二、约定内容

### 1. 创建请求

```json
{
  "job_type": "DRAFT",
  "trace_id": "trace-draft-0001",
  "input": {
    "repository": { "url": "https://github.com/241880199/DevOps",
                    "commit": "d47a1523beec3311033eabf2e74c2a6ac299720d" },
    "build": { "command": "make", "verify_command": "./hello", "verify_expect": "hello E3",
               "project_subdir": "fixtures/draft" },
    "runtime_capabilities": ["ptrace"],
    "limits": { "max_iterations": 5, "timeout_seconds": 600 },
    "context_documents": ["README.md"]
  }
}
```

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `job_type` | 是 | 固定 `DRAFT` |
| `trace_id` | 否 | 透传的追踪号 |
| `input.repository.url` | 是 | 仓库地址 |
| `input.repository.commit` | 否 | **可缺省、可给缩写**——生成方负责解析：缺省取默认分支 HEAD，缩写解析为对应提交。产出一律回报完整 40 位 |
| `input.build.command` | 是 | 第一层判据：构建命令，退出码 0 且产物存在 |
| `input.build.verify_command` | 是 | 第二层判据：功能验证命令 |
| `input.build.verify_expect` | 否 | 期望输出；缺失时只校验退出码 |
| `input.build.project_subdir` | 否 | 项目根相对仓库根的路径，默认 `.`。**必须是仓库内的相对路径**，不接受绝对路径与 `..` |
| `input.runtime_capabilities` | 否 | 本次生成的环境需要的运行能力（v1 只有 `ptrace`）。由调用方提出，生成方固定进环境记录 |
| `input.limits.max_iterations` / `.timeout_seconds` | 是 | 执行预算，超限写 `EXEC_4002` |
| `input.context_documents` | 否 | 供生成时读取的项目文档，最多 2 个 |

`job_id` 不得出现在请求中——它由服务端产生。响应 `202` 表示已受理，不表示已完成。

### 2. 成功输出

```json
"output": {
  "environment_id": "env-draft-fixture-mode0",
  "dockerfile_artifact_id": "dockerfile-001",
  "image_artifact_id": "image-ref-001",
  "resolved_commit": "d47a1523beec3311033eabf2e74c2a6ac299720d",
  "iterations": [
    { "round": 0, "action": "INITIAL", "reason": "...", "outcome": "BUILD_OK" }
  ],
  "result": { "build_ok": true, "artifact_present": true, "verify_ok": true,
              "verify_stdout": "hello E3\n", "rounds_used": 1 }
}
```

| 字段 | 语义边界 |
| --- | --- |
| `environment_id` | **环境的产出**：平台全局唯一的环境身份。下游照抄此值，不自行命名 |
| `image_artifact_id` | 起容器用，指向一条 `IMAGE_REF` 产物；与环境记录里的 `image` 是同一个编号 |
| `resolved_commit` | 实际使用的完整 40 位 SHA。检测基线必须等于它 |
| `dockerfile_artifact_id` | 取 Dockerfile 原文 |
| `iterations[].reason` / `.outcome` | 每一轮为什么这么改、结果如何。`outcome` 取 `BUILD_OK` / `BUILD_FAILED` / `VERIFY_OK` / `VERIFY_FAILED` |
| `result.build_ok`、`artifact_present` | 第一层：编译通过且产物确实生成 |
| `result.verify_ok` | 第二层：功能验证通过 |

**不变式**：`status = SUCCEEDED` 蕴含 `build_ok`、`artifact_present`、`verify_ok` 均为 `true`，且 `environment_id` 指向一个可查询的环境。

**两层判据缺一不可**：构建通过只是第一层，环境能构建不等于它可用；第二层由 `verify_command` 与 `verify_expect` 表达。迭代过程中的某一轮失败属于过程状态，写进 `iterations[].outcome`，不是 `job.error`。

### 3. 输入字段怎么变成环境

| 生成请求里的字段 | 生成结果里的字段 | 注意 |
| --- | --- | --- |
| `build.command` | `Environment.build_command` | 原样成为环境约定 |
| `build.project_subdir` | `Environment.project_root` | **语义不同**：前者是仓库内相对路径，后者是容器内位置 |
| `runtime_capabilities` | `Environment.runtime_capabilities` | 需求由调用方提出，生成方固定 |
| `build.verify_command` / `verify_expect` | 不进入环境 | 它们是**本次任务**的成功判据，不是环境属性 |

**产物归属**：环境生成服务自己的产物（`DOCKERFILE` / `BUILD_LOG` / `VERIFY_LOG` / `IMAGE_REF`）`environment_id` 一律为 `null`——产出时环境尚不存在。

## 三、可执行的最小检查

运行 `python scripts/mock_server.py` 后实测：

| 用例 | 期望结果 |
| --- | --- |
| 创建环境生成任务 | `202` → `SUCCEEDED`，输出含 `environment_id` 与 `image_artifact_id` |
| 用该 `environment_id` 创建检测或修复任务 | `202`，正常受理 |
| `commit` 给 7 位缩写 | `202` → `SUCCEEDED`，`resolved_commit` 为完整 40 位 |
| 完全不给 `commit` | 解析默认分支 HEAD 并回报完整 SHA |
| 给一个格式合法但仓库中不存在的 SHA | `400`（受理阶段，`REQ_1001`）——生成方必须在产出前解析并确认提交真实存在，不产出带假提交的记录 |
| `project_subdir` 是绝对路径或含 `..` | `400` |
| `job_id` 出现在请求里 | `400` |
