# 修复缺失依赖

- **端点**：`POST /v1/repair-jobs`
- **`job_type`**：`REPAIR`
- **生产侧**：依赖修复服务（MDFixer）
- **消费侧**：重新构建与复检的调度方、平台任务入口、需要审查补丁的维护者
- **上游输入**：依赖检测服务产出的错误报告（见 `全量依赖检测.md`、`增量依赖检测.md`）
- **状态**：已采用，**待双方确认后冻结**
- **可执行实现与样例**：`contracts/job-input-repair.schema.json`、`contracts/job-output-repair.schema.json`、`contracts/error-report.schema.json`；设计理由见 `docs/ADR/ADR-005`、`ADR-006`、`ADR-011`

## 一、生产侧与消费侧

修复环节**两头都连着别人**，说清楚方向才不会把「谁等谁」弄反：

| 方向 | 谁 | 交什么 |
| --- | --- | --- |
| 上游输入方 | 依赖检测服务 | 依赖问题报告（作为产物交接，按 `artifact_id` 取回） |
| 生产侧 | 依赖修复服务 | 补丁与修复报告 |
| 下游消费方 | 重新构建与复检的调度方、需要审查补丁的维护者 | — |

修复**只针对缺失依赖**（MD）。冗余声明（RD）的去留由维护者决定，修复不改动它——越界改动会让补丁在评审时被要求拆分。

任务生命周期与共享状态机一致：创建返回 `202` + `QUEUED`，后台转 `RUNNING`，终态为 `SUCCEEDED` / `FAILED` /
`TIMED_OUT` / `CANCELLED`。`output` 与 `error` **只在终态出现**——`QUEUED` / `RUNNING` 期间查询只返回任务元数据。

## 二、输入

| 字段 | 必填 | 语义边界 |
| --- | --- | --- |
| `repository.url` | 是 | 仓库地址，须可由修复环境克隆（`https://`） |
| `repository.commit` | 是 | **完整 40 位** SHA，不接受缩写——报告里每条发现都带完整 SHA，版本比对必须逐字符相等。必须与报告所依据的版本一致 |
| `report.artifact_id` | 是 | 报告的**全局产物编号**，唯一的取回依据（`GET /v1/artifacts/{artifact_id}`） |
| `report.artifact_uri` | 否 | 报告的原始地址，只作对照；填了必须与产物记录里的 `uri` 一致 |
| `report.finding_type` | 是 | 固定 `MISSING`：请求修复冗余依赖会被拒绝 |
| `report.commit` | 否 | 报告所依据的版本 SHA。填了就在**受理阶段**比对（不符直接 `400`），不填则退回执行阶段取回报告后校验 |
| `environment_id` | 是 | 修复所依据的环境；镜像、项目根与构建命令都从环境读取 |
| `makefile_path` | 否 | 构建脚本相对环境项目根的路径，默认 `Makefile` |
| `verification.verify_command` | 是 | 验证修改是否生效，在环境的项目根下执行 |
| `verification.recheck_command` | 是 | 复检依赖问题（通常为重新调用检测服务）。**必填**：输出里的 `recheck_ok` 是「补丁是否真的消除了依赖问题」的唯一依据，不跑复检就无法断言它——这一条与「`fixed` 非空则 `verification` 三项为真」的不变式是同一个要求的两面 |
| `limits.max_iterations` / `.timeout_seconds` | 是 | 执行预算，超限写 `EXEC_4002` |

**验证命令留在请求里，不并入环境。** 环境只回答「在哪里、以什么方式执行」；「这次改动算不算修好」是修复任务自己的判据。同一环境下的复构建与复检才可比，这一点由 `environment_id` 保证。

### 报告怎么消费

| 需要什么 | 为什么 |
| --- | --- |
| 每条发现的 `location` 与 `evidence` | 光有 `(target, dependency)` 无法复核：不知道去哪一行确认、凭什么这么说 |
| `provenance` 区分工具与人工 | 人工标准答案不能混进工具准确率统计 |
| 报告的 `repository.commit` | 补丁能否干净应用的前提；与请求不一致时报告失效 |

**路径基准是环境的 `project_root`**：报告说 `location.file = Makefile`，就该在环境的项目根下有这个文件。请求里不再有独立的 `project_subdir`——同一个「项目根」概念只保留一处定义。

**报告有四种不可用情形，都在受理阶段被拒绝**（`REPAIR_6001`）：

| 情形 | 为什么不能受理 |
| --- | --- |
| 编号取不到对应产物 | 修复没有可依据的目标 |
| 产物类型不是 `ERROR_REPORT` | 拿一份 Dockerfile 或补丁当报告，修复会在错误的输入上跑完全程 |
| 报告属于**另一个环境** | 不同环境下的依赖结论不可比 |
| 报告里**没有 `MISSING` 发现** | 没有可修复的目标时，「修复」这个动作没有意义 |

版本不符分两处收场：请求声明了 `report.commit` 时在受理阶段即以 `400` 拒绝；未声明时，任务会创建，
在执行阶段取回报告后比对，不符以 `FAILED / REPAIR_6001` 结束——**不拿失效的报告去生成补丁**。

## 三、输出

| 字段 | 说明 |
| --- | --- |
| `patch_artifact_id` | 补丁产物引用（`PATCH`）。无可采纳补丁时缺失 |
| `resolved_commit` | 实际使用的 commit SHA，供下游确认报告与补丁指向同一版本 |
| `fixed[]` | 已修复的发现：`target`、`dependency`、`style`（`TARGET` / `MACRO` / `HYBRID` / `IMPLICIT`）、`strategy` |
| `rejected[]` | 被拒绝的候选及原因。**拒绝不是失败**——拒掉一个会引入新问题的候选是正确行为，但必须留痕 |
| `declaration_style_note` | 对项目声明风格的说明，供维护者审查补丁时对照 |
| `verification.build_ok` / `.test_ok` / `.recheck_ok` | 三项独立判据：构建通过、功能与原行为一致、原缺失依赖消失且未引入新的依赖问题 |

补丁保持原项目的声明风格，不重写为另一种；补丁内路径以环境的 `project_root` 为基准。

补丁作为产物交接，记录字段与共享 Artifact 结构一致，其中三项需要本接口专门约定：

| 字段 | 取值 |
| --- | --- |
| `type` | `PATCH`（产出方矩阵只允许依赖修复服务产出） |
| 存储域 | `mdfixer` |
| `environment_id` | 补丁产出时所处的环境，即本次请求的 `environment_id`（非 `null`——产出时环境已存在） |
| `source_commit` | 等于输出的 `resolved_commit`，保证补丁可追溯到它针对的源码版本 |

### 成功判据与失败边界

| 情形 | `status` | `output` | 下游怎么理解 |
| --- | --- | --- | --- |
| 产出了可采纳补丁 | `SUCCEEDED` | `fixed` 非空，`verification` 三项为真 | 有补丁可用 |
| 全部候选都被拒绝 | `SUCCEEDED` | `fixed` 为空数组，`rejected` 非空 | 没有补丁可用，逐条看拒绝理由 |
| 报告取不到 / 版本不符 | `FAILED` | — | `REPAIR_6001`：修复没有可信的输入 |
| 补丁工具跑不起来 | `FAILED` | — | `REPAIR_6002`：修复过程本身没跑成 |

判据是**「做完判断」与「判断没做成」**：`rejected[]` 是做完判断的结论（判 `FAILED` 的话，那些理由就没有地方存放）；`6xxx` 是判断没做成。这条边界最容易画错，混同的后果是调度器把一次带明确理由的结论当成基础设施故障重跑。

两条不变式：

- `fixed` 非空 ⟹ `verification` 三项均为 `true`；
- `fixed` 为空 ⟹ `rejected` 非空，且不带 `patch_artifact_id`。

## 四、可执行的最小检查

在 `main` 分支执行 `python scripts/validate.py`（检查 08、09、10、11、14）：修复请求只消费 `MISSING`、
只接受完整 40 位 SHA、复检命令必填、成功输出的两条不变式、固定输入与磁盘上的真实文件一致（报告里的
`location` 能数出来、参考补丁能干净应用且不越界改动冗余声明）、样例提交真实存在、报告记录是
`ERROR_REPORT` 且属于同一环境。

运行 `python scripts/mock_server.py` 后可实测：

| 用例 | 期望结果 |
| --- | --- |
| 有效修复请求 | `202` → `SUCCEEDED`，`fixed` 与 `rejected` 都有内容，补丁可下载 |
| 报告版本与请求不一致 | 受理阶段 `400`（声明了 `report.commit`）或执行阶段 `FAILED / REPAIR_6001` |
| 请求修复冗余依赖 | `400` |
| 输入内嵌环境定义 | `400` |
| 输入仍带 `project_subdir` | `400` |
| 报告的 `artifact_uri` 与产物记录不一致 | `400` |
| 引用的产物不是 `ERROR_REPORT` | `400` |
| 报告属于另一个环境 | `400` |
| 报告里没有 `MISSING` 发现 | `400` |
| `repository.commit` 给缩写 | `400`（必须完整 40 位） |
| 引用未登记的环境 | `400` |

待确认事项：

1. 「报告取不到」的判定责任：请求未声明 `report.commit` 时，服务端要取回报告再校验，取回失败与版本不符是否都用 `REPAIR_6001` 承载（本地实现按「都用」处理）；
2. 报告交付方式：当前约定是检测侧把报告登记为全局产物、修复侧按 ID 取回；是否需要在同一 `trace_id` 下自动串联；
3. `recheck_command` 的实现归属：当前是修复侧执行，若改为回调检测服务，需要新增接口。
