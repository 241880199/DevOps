# 跨接口联调检查清单

各接口文档的「可执行的最小检查」覆盖**单条接口自身**；本清单覆盖**组合起来**的部分——按流水线顺序走一遍，四个环节能接上才算联调通过。

## 一、闭环顺序

```
生成构建环境 → 查询环境定义 → 全量依赖检测 → 下载产物 → 增量依赖检测 → 修复缺失依赖 → 复检
```

| # | 步骤 | 输入从哪来 | 期望 |
| --- | --- | --- | --- |
| 1 | 生成构建环境 | 仓库 + 两层判据 | `202` → `SUCCEEDED`，拿到 `environment_id` 与 `image_artifact_id` |
| 2 | 查询环境定义 | 上一步的 `environment_id` | `200`，六字段齐全；`image` 指向一条 `IMAGE_REF` 产物 |
| 3 | 全量依赖检测 | 上一步的 `environment_id` + `repository` | `202` → `SUCCEEDED`，拿到三个产物编号 |
| 4 | 下载产物 | 上一步的三个编号 | `200`，取回内容按 `sha256` 核验通过 |
| 5 | 增量依赖检测 | 基线图编号 + `base_commit` + 同一 `environment_id` | `202` → `SUCCEEDED`，拿到 `changes` 与报告编号 |
| 6 | 修复缺失依赖 | 报告的 `artifact_id` + 同一 `environment_id` | `202` → `SUCCEEDED`，补丁可下载 |
| 7 | 复检 | 应用补丁后重跑一次增量检测 | 原缺失依赖消失，且未引入新的依赖问题 |

## 二、跨接口的一致性检查

单条接口自己看不出来的问题，都在这一组里：

| 检查 | 具体断言 |
| --- | --- |
| **版本一致** | 检测基线的 commit 等于环境生成回报的 `resolved_commit`；报告的 commit 等于修复请求的 `repository.commit` |
| **环境一致** | 同一轮里的检测与修复引用同一个 `environment_id`；基线图的 `environment_id` 等于本次检测的 |
| **摘要一致** | 每个产物取回后按记录里的 `sha256` 与 `size_bytes` 核验内容完整 |
| **归属一致** | 环境生成服务的产物 `environment_id` 为 `null`；检测与修复的产物记录所属环境 |
| **编码一致** | 受理阶段的拒绝用 `REQ_1xxx`，不写进任务终态的 `error`；任务错误码只出现在终态 |
| **语义一致** | 检出 MD / RD 的任务终态是 `SUCCEEDED`，不是 `FAILED` |
| **可查一致** | 任一 `job_id`、`environment_id`、`artifact_id` 都能按对应的查询端点取到；未登记的返回 `404` / `REQ_1002` |

## 三、已知的未闭环处

联调时会碰到、但按当前契约**就是这样**的三处：

| 项 | 现状 |
| --- | --- |
| **多轮增量** | 靠「一轮基线 + 逐轮 `changes`」链式累积。需要一张「当前的实际图」时，重跑一次全量检测，不让增量检测交推断图 |
| **复检的实现** | 由修复侧执行 `recheck_command`，不是回调检测服务 |
| **RD 没有修复者** | 报告如实包含 `REDUNDANT`，但修复只针对 `MISSING`；冗余声明的去留由维护者决定 |

## 四、怎么跑

```bash
python scripts/mock_server.py --port 8080
```

四类任务与两个查询端点（任务、产物、环境）都有模拟执行路径；`FULL_CHECK` 与 `INCREMENTAL_CHECK` 会动态登记可下载的图与报告，但**不运行真实检测器**——空图、空报告只用于验证契约与交接流程。

契约层面的自动校验是 `python scripts/validate.py`（退出码 0 表示全部通过），它覆盖样例与 schema 的一致性；本清单覆盖的是**跨接口的组合**，两者互补。
