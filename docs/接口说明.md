# 接口说明

面向**下游消费方**的对接文档，覆盖四类耗时任务。

| 任务类型 | 服务 | 契约状态 |
| --- | --- | --- |
| `DRAFT` | 环境生成 | ✅ 已定稿 |
| `REPAIR` | 依赖修复 | ✅ 已定稿 |
| `FULL_CHECK` | 全量依赖检测 | ✅ A03 已确认并补齐输出契约 |
| `INCREMENTAL_CHECK` | 增量依赖检测 | ✅ A03 已确认并补齐输出契约 |

- 契约权威来源：`contracts/*.schema.json`
- 错误语义详解：`contracts/error-codes.md`
- 可执行校验：`python scripts/validate.py`

---

## 1. 端点

| 操作 | 方法与路径 | job_type |
| --- | --- | --- |
| 生成构建环境 | `POST /v1/dockerfile-jobs` | `DRAFT` |
| 全量依赖检测 | `POST /v1/full-check-jobs` | `FULL_CHECK` |
| 增量依赖检测 | `POST /v1/incremental-check-jobs` | `INCREMENTAL_CHECK` |
| 修复缺失依赖 | `POST /v1/repair-jobs` | `REPAIR` |
| 查询任务 | `GET /v1/jobs/{job_id}` | 全部 |
| 下载产物 | `GET /v1/artifacts/{artifact_id}` | 全部 |

创建请求中的 `job_type` 必须与端点一致，不一致会被拒绝。

**所有任务采用异步模型**：创建只做受理，返回 `202` 与 `job_id`，执行在后台进行。理由见 `docs/ADR/ADR-001`。

---

## 2. 交接什么

### 2.1 环境生成（DRAFT）交给下游

| 交接物 | 字段 | 下游用途 |
| --- | --- | --- |
| 可运行镜像 | `output.image_ref` | 起容器，在其中执行全量/增量构建 |
| Dockerfile | `output.dockerfile_artifact_id` → 产物 | 需要重建、审查或复现环境时取用 |
| 实际使用的版本 | `output.resolved_commit` | **对齐基线**：检测所依据的 commit 必须与此一致 |
| **构建配置标识** | `output.configuration_id` | **对齐基线**：与 commit 共同确定基线身份，检测输入里的 `environment.configuration_id` 直接沿用此值（见 ADR-007） |
| 每轮迭代记录 | `output.iterations[]` | 排查「环境为什么是这样搭的」 |
| 构建与验证结论 | `output.result` | 判断环境是否真的可用 |

### 2.2 依赖检测交给修复（REPAIR）

| 交接物 | 字段 | 下游用途 |
| --- | --- | --- |
| 依赖问题报告 | `report` → 产物（`error-report.schema.json`） | 修复的目标来源 |
| 报告所依据的版本 | `report.commit` | **校验报告是否失效**：与环境生成输出的 `resolved_commit`、以及请求的 `repository.commit` 必须一致 |
| 问题规模 | 报告的 `summary` | 评估修复工作量 |

修复请求必须把报告的 `finding_type` 限定为 `MISSING`——修复只针对缺失依赖。

### 2.3 本服务需要下游提供

| 需要明确 | 说明 |
| --- | --- |
| 版本对齐 | 下游检测所依据的 commit，必须与环境生成输出的 `resolved_commit` 一致 |
| 报告版本 | 修复请求的 `report.commit` 须与 `repository.commit` 一致；报告版本不符时以 `REPAIR_6001` 拒绝，补丁按失效报告生成必然打不上 |
| 环境有效性判据 | 若除「能构建」外还要求「能运行测试」，通过 `build.verify_command` 与 `verify_expect` 表达 |
| 项目根目录 | 仓库根不是构建根时，用 `build.project_subdir` 指定（DRAFT）或 `project_subdir`（REPAIR） |
| 产物读取方式 | 本地路径映射还是调用下载接口，需双方事先约定（见第 9 节） |

## 3. DRAFT：创建任务

`POST /v1/dockerfile-jobs`

```json
{
  "job_type": "DRAFT",
  "trace_id": "trace-draft-0001",
  "input": {
    "repository": { "url": "https://github.com/241880199/DevOps", "commit": "b06e66e" },
    "build": { "command": "make", "verify_command": "./hello", "verify_expect": "hello draft",
               "project_subdir": "fixtures/draft" },
    "limits": { "max_iterations": 5, "timeout_seconds": 600 },
    "context_documents": ["README.md"]
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `job_type` | ✅ | 固定 `DRAFT` |
| `trace_id` | ⬜ | 透传的追踪号 |
| `input.repository.url` | ✅ | 仓库地址 |
| `input.repository.commit` | ⬜ | 建议给**完整** SHA；缺失时取默认分支 HEAD 并在 `resolved_commit` 回报 |
| `input.build.command` | ✅ | **第一层判据**：构建命令 |
| `input.build.verify_command` | ✅ | **第二层判据**：功能验证命令 |
| `input.build.verify_expect` | ⬜ | 期望输出；缺失时只校验退出码 |
| `input.build.project_subdir` | ⬜ | 项目根相对仓库根的路径，默认 `.`。构建与验证命令都在该目录下执行 |
| `input.limits.max_iterations` | ✅ | 迭代轮数上限，1–20 |
| `input.limits.timeout_seconds` | ✅ | 单次构建墙钟上限（秒） |
| `input.context_documents` | ⬜ | 供生成时读取的项目文档，**最多 2 个** |

> **`project_subdir` 别漏。** 仓库根不是构建根时（本仓库自己就是——可构建的样例在 `fixtures/draft/`），漏填的后果是 DRAFT 在仓库根跑 `make`，然后以「构建不通过」收场；而真实原因只是找错了目录。这类失败**看起来像项目本身的问题**，很难从迭代记录里反推出来。

> **`job_id` 不得出现在请求中**——它由服务端产生，携带即被拒绝。

响应 `202 Accepted`：

```json
{ "job_id": "job-draft01", "job_type": "DRAFT", "status": "QUEUED",
  "trace_id": "trace-draft-0001", "created_at": "2026-09-20T10:00:00Z" }
```

**`202` 表示已受理，不表示已完成。**

## 4. DRAFT：输出

`GET /v1/jobs/{job_id}` → `200 OK`

```json
"output": {
  "dockerfile_artifact_id": "dockerfile-001",
  "image_ref": "draft-fixture-ok:1.0",
  "resolved_commit": "b06e66ec9f3d2a1b4c5e6f708192a3b4c5d6e7f8",
  "configuration_id": "cc-MODE0",
  "iterations": [
    { "round": 0, "action": "INITIAL", "reason": "...", "outcome": "BUILD_OK" },
    { "round": 1, "action": "PATCH", "reason": "...", "outcome": "VERIFY_OK" }
  ],
  "result": { "build_ok": true, "artifact_present": true, "verify_ok": true,
              "verify_stdout": "hello draft\n", "rounds_used": 1 }
}
```

| 字段 | 下游怎么用 |
| --- | --- |
| `image_ref` | **起容器用**，可直接 `docker run` |
| `resolved_commit` | **对齐基线用**，检测基线 commit 必须等于它 |
| `configuration_id` | **对齐基线用**，检测输入的 `environment.configuration_id` 直接沿用此值，不要自行命名（见 ADR-007）。可选，缺失时需双方另行约定 |
| `dockerfile_artifact_id` | 取 Dockerfile 原文 |
| `iterations[].reason` | **为什么这么改**——环境异常时的首要排查线索 |
| `iterations[].outcome` | `BUILD_OK` / `BUILD_FAILED` / `VERIFY_OK` / `VERIFY_FAILED` |
| `result.build_ok`、`artifact_present` | 第一层：编译通过且产物确实生成 |
| `result.verify_ok` | 第二层：功能验证通过 |

> **下游不要只看 `status`。** 用 `result.verify_ok` 确认环境**真的能跑**，而不只是能编译。
>
> **不变式**：`status = SUCCEEDED` 蕴含 `build_ok`、`artifact_present`、`verify_ok` 均为 `true`。观察到不一致属契约违反。

## 5. REPAIR：创建任务

`POST /v1/repair-jobs`

```json
{
  "job_type": "REPAIR",
  "trace_id": "trace-repair-0001",
  "input": {
    "repository": { "url": "https://github.com/241880199/DevOps", "commit": "b06e66ec..." },
    "report": {
      "artifact_id": "md-report-001",
      "artifact_uri": "artifact://b03/job-oracle-mdfixer01/error-report.json",
      "finding_type": "MISSING",
      "commit": "b06e66ec..."
    },
    "project_subdir": "fixtures/mdfixer",
    "makefile_path": "Makefile",
    "environment": {
      "image_ref": "mdfixer-fixture:1.0",
      "build_command": "make",
      "verify_command": "./app",
      "recheck_command": "make clean && make"
    },
    "limits": { "max_iterations": 3, "timeout_seconds": 300 }
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `input.repository.url` / `.commit` | ✅ | 必须与报告所依据的版本一致，否则报告失效（`REPAIR_6001`） |
| `input.report.artifact_id` / `.artifact_uri` | ✅ | 问题报告引用 |
| `input.report.finding_type` | ✅ | **固定 `MISSING`**。请求修复冗余依赖会被拒绝 |
| `input.report.commit` | ⬜ | 报告所依据的版本 SHA。**建议填**——填了就在受理阶段比对，不填则要取回报告后才发现不符 |
| `input.project_subdir` | ⬜ | 项目根相对仓库根的路径，默认 `.`。报告里的 `location.file` 与 `makefile_path` 都相对这个根解析 |
| `input.makefile_path` | ⬜ | 构建脚本路径，默认 `Makefile` |
| `input.environment.image_ref` | ✅ | 修复所依据的环境，须与产出补丁后的复构建环境一致 |
| `input.environment.build_command` | ✅ | 复构建命令 |
| `input.environment.verify_command` | ✅ | 验证修改是否生效 |
| `input.environment.recheck_command` | ⬜ | 复检依赖问题；缺失时只做构建与功能验证 |
| `input.limits` | ✅ | 迭代轮数与超时 |

> **`report.commit` 与 `repository.commit` 不一致会发生什么。** 填了 `report.commit` 的话，请求在受理阶段就被 `400` 拒绝（`error.code = REPAIR_6001`），不创建任务；不填的话，任务会创建，执行阶段取回报告后发现不符，任务以 `REPAIR_6001` 失败。两种情形是同一个事实，只是发现得早晚不同。

## 6. REPAIR：输出

```json
"output": {
  "patch_artifact_id": "patch-0001",
  "resolved_commit": "b06e66ec...",
  "fixed": [
    { "target": "main.o", "dependency": "config.h", "style": "TARGET",
      "strategy": "在该目标的依赖列表中直接追加依赖项" }
  ],
  "rejected": [
    { "target": "main.o", "dependency": "unused.h",
      "reason": "候选补丁顺带删除了这条冗余声明。修复只针对缺失依赖，冗余声明的去留由维护者决定，越界改动不予采纳" }
  ],
  "declaration_style_note": "Makefile 使用原子依赖列表，未经宏组织……",
  "verification": { "build_ok": true, "test_ok": true, "recheck_ok": true }
}
```

| 字段 | 说明 |
| --- | --- |
| `patch_artifact_id` | 补丁产物引用。无可采纳补丁时缺失 |
| `fixed[].style` | 原声明风格：`TARGET` 原子列表 / `MACRO` 经宏组织 / `HYBRID` 混合 / `IMPLICIT` 隐式规则 |
| `fixed[].strategy` | 采用的修补手段，供维护者判断改动是否可接受 |
| `rejected[].reason` | **被拒绝的候选及原因**。拒绝不是失败——拒掉一个会引入新问题的候选是正确行为，但必须留痕 |
| `verification.build_ok` | 应用补丁后构建通过 |
| `verification.test_ok` | 功能验证通过且与原行为一致 |
| `verification.recheck_ok` | **复检后原缺失依赖已消失，且未引入新的依赖问题** |

> 三项判据缺一不可。`recheck_ok` 是最关键的一条：补丁改对了位置但没有真正消除问题，与前两项都通过并不矛盾。注意它的措辞是「未**引入**新的依赖问题」——报告里原有的冗余声明若未被动过，不算引入新问题。

### 怎么判断这次修复成功了没有

**不要只看 `status`。** 修复服务的成功判据是「给出判断」，不是「产出补丁」，所以两种情形都是 `SUCCEEDED`：

| 情形 | `status` | `output` | 下游怎么理解 |
| --- | --- | --- | --- |
| 产出了可采纳补丁 | `SUCCEEDED` | `fixed` 非空，`verification` 三项为真 | 有补丁可用，取 `patch_artifact_id` |
| **所有候选都被拒绝** | `SUCCEEDED` | `fixed` 为空数组，`rejected` 非空 | **没有补丁可用**，逐条看 `rejected[].reason` 判断是否要人工介入 |
| 报告取不到 / 版本不符 | `FAILED` | — | `error.code = REPAIR_6001`，修复没有可信的输入 |
| 补丁工具跑不起来 | `FAILED` | — | `error.code = REPAIR_6002`，修复过程本身没跑成 |

判据是**「做完判断」与「判断没做成」**：

- `rejected[]` 是**做完判断**的结果——候选被正常评估过，只是结论为「不可接受」。这是产出，必须留痕。
- `REPAIR_6001` / `REPAIR_6002` 是**判断没做成**——输入不可信，或工具跑不起来。

**「全部候选被拒」为什么不判 `FAILED`**：`FAILED` 的任务没有 `output`，`rejected[]` 里那些理由就没地方放了。详见 `docs/ADR/ADR-006` 与 `contracts/error-codes.md` 第 6 节。

### 两条不变式

- `fixed` 非空 ⟹ `verification.build_ok` / `test_ok` / `recheck_ok` 均为 `true`；
- `fixed` 为空 ⟹ `rejected` 非空，且**不带** `patch_artifact_id`。

由 `scripts/validate.py` 检查 08 强制。

## 7. 依赖问题报告契约

检测服务产出、修复服务消费，作为 artifact 以 URI 引用交接。结构见 `contracts/error-report.schema.json`，决策理由见 `docs/ADR/ADR-005`。

```json
{
  "schema_version": "1.0",
  "repository": { "url": "...", "commit": "b06e66ec..." },
  "configuration_id": "cc-MODE0",
  "produced_by": { "detector": "BuildChecker", "job_id": "job-full01", "mode": "FULL" },
  "generated_at": "2026-09-20T09:40:00Z",
  "summary": { "missing": 2, "redundant": 1 },
  "findings": [
    {
      "type": "MISSING",
      "target": "main.o",
      "dependency": "config.h",
      "commit": "b06e66ec...",
      "detector": "BuildChecker",
      "provenance": "TOOL",
      "location": { "file": "Makefile", "line": 7, "detail": "只声明了 main.c" },
      "evidence": { "kind": "FILE_ACCESS", "detail": "构建期间读取了 config.h" }
    }
  ]
}
```

### 两条容易忽略的约定

**每条发现必须同时带 `location` 与 `evidence`。** 光有 `(target, dependency)` 无法复核——复核者不知道去哪一行确认，也不知道判定依据。缺任一者报告不可复核。

**`provenance` 显式区分工具与人工来源。** `detector` 说明是**哪个**工具，`provenance` 说明是哪**一类**来源（`TOOL` / `INSTRUCTOR_ORACLE` / `MANUAL`）。消费方过滤人工样本时判断枚举值即可，不必猜测检测器的命名约定——靠字符串约定会让统计静默失真。

报告**可以同时包含** `MISSING` 与 `REDUNDANT`（如实反映检测结果）；修复请求把范围限定为 `MISSING`，边界在请求侧收窄，而不是在报告侧裁剪。

## 8. 错误码与状态语义

### 状态机

```
QUEUED ──> RUNNING ──┬──> SUCCEEDED    结果可用，output 必填，不得携带 error
   │                 ├──> FAILED       error 必填
   │                 └──> TIMED_OUT    error 必填
   └─────────────────> CANCELLED       error 必填
```

- `output` 与 `error` **只在终态出现**：`QUEUED` / `RUNNING` 阶段只返回任务元数据。
- 终态一经到达不再变更。

> **为什么执行中不回传部分结果。** 若允许 `RUNNING` 携带部分 `output`，消费方就要同时处理两种输出形状，字段必填性也会随状态浮动，schema 无法静态约束。理由见 `docs/ADR/ADR-004`。

### 错误码

| 错误码 | 含义 | 下游应如何反应 |
| --- | --- | --- |
| `ENV_3002` | 镜像构建失败 | 环境不可用。**不要**在缺环境的情况下继续检测 |
| `EXEC_4002` | 任务超时 | 可考虑放宽 `limits.timeout_seconds` 后重试 |
| `ANALYSIS_5001` | 分析器失败 | 由检测服务产出 |
| `REPAIR_6001` | 修复输入不可用：报告取不到 / 不符合契约 / 版本与请求不符 | 修复没有可信的输入。重新取报告或修正 `repository.commit` 后再提交，**不要**原样重试 |
| `REPAIR_6002` | 修复过程无法进行：缺补丁工具、工作副本不可写 | 环境问题（通常是 `image_ref` 里缺 `git`/`patch`），修环境后重试 |

### 最关键的一条

**「发现问题」不等于「执行失败」。**

检出缺失依赖说明检测服务**正常完成了工作**，任务终态是 `SUCCEEDED`，发现写入报告产物，**不是** `error`。把「发现 MD」写成 `FAILED` 会让调度器把成功分析当故障重试。

对环境生成：某一轮候选构建失败但已定位原因、继续迭代，属于过程状态，记入 `iterations[].outcome`，**不写入** `job.error`。

对修复：候选被评估后判定不可接受（`rejected[]`）同样是过程状态，不影响任务终态——**即使所有候选都被拒绝**，任务仍是 `SUCCEEDED`。真正写入 `job.error` 的只有 `REPAIR_6001` 与 `REPAIR_6002` 两种「判断没做成」的情形。

### 自检三问

接入方在联调前应确认对以下三问答案一致：

1. 检测服务报告了一条 MD，这个 job 的 `status` 是什么？ → **`SUCCEEDED`**
2. 分析进程段错误崩溃了，这个 job 的 `status` 是什么？ → **`FAILED`**，`error.code = ANALYSIS_5001`
3. 修复服务把所有候选补丁都拒了，这个 job 的 `status` 是什么？ → **`SUCCEEDED`**，`output.fixed` 为空、`output.rejected` 非空

## 9. 产物访问

产物以 URI 引用交接，不内嵌进响应（见 `docs/ADR/ADR-002`）。

```json
{
  "artifact_id": "dockerfile-001",
  "type": "DOCKERFILE",
  "uri": "artifact://b03/job-draft01/Dockerfile",
  "media_type": "text/x-dockerfile",
  "producer_job_id": "job-draft01",
  "sha256": "4120822b8beeb4bdaed9bd1f5c4f17956c95c9dca9645455b2cbd6b65da25846",
  "size_bytes": 539,
  "source_commit": "b06e66ec..."
}
```

修复服务产出的补丁同理：

```json
{
  "artifact_id": "patch-0001",
  "type": "PATCH",
  "uri": "artifact://b03/job-repair01/fix.patch",
  "media_type": "text/x-diff",
  "producer_job_id": "job-repair01",
  "sha256": "b6e14fa1c8d34d93614a279db5c0e36515bdc113fb1cc403c83505017d8fd561",
  "size_bytes": 199,
  "source_commit": "b06e66ec..."
}
```

两个样例的 `sha256` 都取自仓库里真实存在的文件（`fixtures/draft/docker/Dockerfile.ok`、
`fixtures/mdfixer/reference.patch`），由 `scripts/validate.py` 检查 06 逐字节核验。
文件改一个字符，校验就会失败——**摘要不实的产物记录比没有摘要更危险**，
它会让下游的完整性核验变成走过场。

**双方必须事先约定 URI 的解析方式**，二选一：

1. **本地路径映射**——`artifact://<存储域>/<job_id>/<文件名>` 映射到约定的本地目录；
2. **调用下载接口**——`GET /v1/artifacts/{artifact_id}` 取原始字节。

只给出 URI 而不约定解析方式，等于没有交接。`sha256` 用于核验内容完整，`source_commit` 保证产物可追溯到它产出的源码版本。

## 10. 检测类任务契约

`FULL_CHECK` 与 `INCREMENTAL_CHECK` 由 A03 负责。A03 接受原输入形状，并补充了专用输出契约与依赖图契约。

### FULL_CHECK

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `repository.url` / `.commit` | ✅ | 基线必须绑定到具体提交，不接受分支名或标签 |
| `environment.image_ref` | ✅ | 可运行镜像 |
| `environment.configuration_id` | ✅ | 构建配置标识。**与 commit 共同确定基线身份** |
| `build.clean_command` | ✅ | 干净的完整构建命令 |
| `build.project_root` | ✅ | 项目根目录在容器内的路径 |

### INCREMENTAL_CHECK

在 FULL_CHECK 基础上增加：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `base_commit` | ✅ | 基线的完整 SHA |
| `baseline.actual_graph_uri` | ✅ | 基线实际依赖图 |
| `baseline.commit` | ✅ | 应**等于** `base_commit`，不一致时任务被拒绝 |
| `baseline.configuration_id` | ✅ | 应与本次环境配置一致，不一致时结果不可比 |
| `build.incremental_command` | ✅ | 增量构建命令 |

**历史图必须能追溯到 base commit。** 基线不带版本或配置，就无法判断这份图是否适用于当前比较——因此 `baseline` 三项全部必填，且提交与配置必须匹配。

### FULL_CHECK 输出

权威文件：`contracts/job-output-full-check.schema.json`。

输出包含 `resolved_commit`、`configuration_id`、实际依赖图、声明依赖图和错误报告的产物编号，以及 MD/RD 汇总。图文件遵循 `contracts/dependency-graph.schema.json`，报告遵循 `contracts/error-report.schema.json`。决策理由见 `docs/ADR/ADR-008-BuildChecker输出与依赖图交付.md`。

### INCREMENTAL_CHECK 输出

权威文件：`contracts/job-output-incremental-check.schema.json`。

输出同时保留 `base_commit` 与当前 `resolved_commit`，返回更新后的实际依赖图、当前错误报告，并在 `changes.added` 与 `changes.resolved` 中表达相对基线的变化。返回的实际依赖图供下一次增量检测继续使用。决策理由见 `docs/ADR/ADR-009-EChecker基线身份与变化表达.md`。

## 11. 版本与变更政策

`schema_version` 当前为 `1.0`。

| 变更类型 | 例子 | 兼容性 |
| --- | --- | --- |
| 兼容 | 新增**可选**字段 | 消费者须允许未知字段；共享 schema 同步更新 |
| 破坏 | 字段删除、改名、改语义；`status` 或 `job_type` 枚举取值变动 | 必须递增 `schema_version`，双方同步升级 |

`status` 枚举一旦变更，所有消费方的分支逻辑都会失效，属最高风险变更。
