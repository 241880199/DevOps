# 接口说明

面向**下游消费方**的对接文档，覆盖四类耗时任务。

| 任务类型 | 服务 | 契约状态 |
| --- | --- | --- |
| `DRAFT` | 环境生成 | 已迁移到统一任务模型 2.0；环境由本服务产出并提供查询 |
| `REPAIR` | 依赖修复 | 已迁移到统一任务模型 2.0 |
| `FULL_CHECK` | 全量依赖检测 | 依赖检测服务已按共享约定更新；待双方冻结接口文档 |
| `INCREMENTAL_CHECK` | 增量依赖检测 | 依赖检测服务已按共享约定更新；待双方冻结接口文档 |

- 共同契约权威来源：`241880199/DevOps` 的 `contract-phase` 分支
- 本地可执行提案：`contracts/*.schema.json`
- 错误语义详解：`contracts/error-codes.md`
- 可执行校验：`python scripts/validate.py`

---

## 1. 端点

| 操作 | 方法与路径 | job_type |
| --- | --- | --- |
| 生成构建环境 | `POST /v1/dockerfile-jobs` | `DRAFT` |
| 全量依赖检测 | `POST /v1/full-check-jobs` | `FULL_CHECK` |
| 增量依赖检测 | `POST /v1/incremental-check-jobs` | `INCREMENTAL_CHECK` |
| 修复缺失依赖 | `POST /v1/repair-jobs` | `REPAIR` |
| 查询任务 | `GET /v1/jobs/{job_id}` | 全部 |
| 下载产物 | `GET /v1/artifacts/{artifact_id}` | 全部 |
| 查询环境定义 | `GET /v1/environments/{environment_id}` | 全部 |

创建请求中的 `job_type` 必须与端点一致，不一致会被拒绝。

**所有任务采用异步模型**：创建只做受理，返回 `202` 与 `job_id`，执行在后台进行。理由见 `docs/ADR/ADR-001`。

## 2. 交接什么

### 2.1 环境生成（DRAFT）交给下游

| 交接物 | 字段 | 下游用途 |
| --- | --- | --- |
| **环境身份** | `output.environment_id` | **对齐基线**：与 commit 共同确定基线身份。构建命令、项目根、工作目录与运行能力都在这个环境里，用 `GET /v1/environments/{environment_id}` 取（见 ADR-011） |
| 可运行镜像 | `output.image_artifact_id` → `IMAGE_REF` 产物 | 起容器，在其中执行全量/增量构建。环境记录里的 `image` 指向同一条产物 |
| Dockerfile | `output.dockerfile_artifact_id` → 产物 | 需要重建、审查或复现环境时取用 |
| 实际使用的版本 | `output.resolved_commit` | **对齐基线**：检测所依据的 commit 必须与此一致 |
| 每轮迭代记录 | `output.iterations[]` | 排查「环境为什么是这样搭的」 |
| 构建与验证结论 | `output.result` | 判断环境是否真的可用 |

### 2.2 依赖检测交给修复（REPAIR）

| 交接物 | 字段 | 下游用途 |
| --- | --- | --- |
| 依赖问题报告 | `report` → 产物（`error-report.schema.json`） | 修复的目标来源 |
| 报告所依据的版本 | `report.commit` | **校验报告是否失效**：与环境生成输出的 `resolved_commit`、以及请求的 `repository.commit` 必须一致 |
| 问题规模 | 报告的 `summary` | 评估修复工作量 |

修复请求必须把报告的 `finding_type` 限定为 `MISSING`——修复只针对缺失依赖。

### 2.3 本服务需要下游提供

| 需要明确 | 说明 |
| --- | --- |
| 版本对齐 | 下游检测所依据的 commit，必须与环境生成输出的 `resolved_commit` 一致 |
| 报告版本 | 修复请求的 `report.commit` 须与 `repository.commit` 一致；报告版本不符时以 `REPAIR_6001` 拒绝，补丁按失效报告生成必然打不上 |
| 环境有效性判据 | 若除「能构建」外还要求「能运行测试」，通过 `build.verify_command` 与 `verify_expect` 表达 |
| 项目根目录 | 仓库根不是构建根时，DRAFT 用 `build.project_subdir` 指定；下游任务不重复传，改用环境的 `project_root`（容器内位置） |
| 运行能力 | 检测要读文件访问记录（`ptrace`），这是**环境的需求**：由环境记录声明，需要新能力时新建一个环境 |
| 产物读取方式 | 一律经下载接口 `GET /v1/artifacts/{artifact_id}` 取回；`uri` 是给人的原始地址，不是寻址依据（见第 9 节） |

## 3. DRAFT：创建任务

`POST /v1/dockerfile-jobs`

```json
{
  "job_type": "DRAFT",
  "trace_id": "trace-draft-0001",
  "input": {
    "repository": { "url": "https://github.com/241880199/DevOps",
                    "commit": "d47a1523beec3311033eabf2e74c2a6ac299720d" },
    "build": { "command": "make", "verify_command": "./hello", "verify_expect": "hello E3",
               "project_subdir": "fixtures/draft" },
    "limits": { "max_iterations": 5, "timeout_seconds": 600 },
    "context_documents": ["README.md"]
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `job_type` | ✅ | 固定 `DRAFT` |
| `trace_id` | ⬜ | 透传的追踪号 |
| `input.repository.url` | ✅ | 仓库地址 |
| `input.repository.commit` | ⬜ | 建议给**完整** SHA；缺失时取默认分支 HEAD 并在 `resolved_commit` 回报 |
| `input.build.command` | ✅ | **第一层判据**：构建命令 |
| `input.build.verify_command` | ✅ | **第二层判据**：功能验证命令 |
| `input.build.verify_expect` | ⬜ | 期望输出；缺失时只校验退出码 |
| `input.build.project_subdir` | ⬜ | 项目根相对仓库根的路径，默认 `.`。构建与验证命令都在该目录下执行 |
| `input.limits.max_iterations` | ✅ | 迭代轮数上限，1–20 |
| `input.limits.timeout_seconds` | ✅ | 单次构建墙钟上限（秒） |
| `input.runtime_capabilities` | ⬜ | 本次生成的环境需要的运行能力（v1 只有 `ptrace`）。**需求方信息**：调用方知道后续要在这个环境里做什么，环境生成服务据此写进环境记录；缺省为空数组 |
| `input.context_documents` | ⬜ | 供生成时读取的项目文档，**最多 2 个** |

> **`project_subdir` 必须是仓库内的相对路径。** 不接受绝对路径，也不接受含 `..` 的路径——它会被拼成容器内的项目根，越界之后构建与验证就作用到别的目录上（`../../etc` 会让 `project_root` 逃出工作区）。请求里的 `project_subdir` 与 `makefile_path` 都按这条规则校验；环境记录里的 `project_root` 允许是容器内绝对路径，但必须落在工作区之内。

> **`project_subdir` 别漏。** 仓库根不是构建根时（本仓库自己就是——可构建的样例在 `fixtures/draft/`），漏填的后果是 DRAFT 在仓库根跑 `make`，然后以「构建不通过」收场；而真实原因只是找错了目录。这类失败**看起来像项目本身的问题**，很难从迭代记录里反推出来。

> **`job_id` 不得出现在请求中**——它由服务端产生，携带即被拒绝。

响应 `202 Accepted`：

```json
{ "job_id": "job-draft01", "job_type": "DRAFT", "status": "QUEUED",
  "trace_id": "trace-draft-0001", "created_at": "2026-09-20T10:00:00.000Z" }
```

**`202` 表示已受理，不表示已完成。**

## 4. DRAFT：输出

`GET /v1/jobs/{job_id}` → `200 OK`

```json
"output": {
  "environment_id": "env-draft-fixture-mode0",
  "dockerfile_artifact_id": "dockerfile-001",
  "image_artifact_id": "image-ref-001",
  "resolved_commit": "d47a1523beec3311033eabf2e74c2a6ac299720d",
  "iterations": [
    { "round": 0, "action": "INITIAL", "reason": "...", "outcome": "BUILD_OK" },
    { "round": 1, "action": "PATCH", "reason": "...", "outcome": "VERIFY_OK" }
  ],
  "result": { "build_ok": true, "artifact_present": true, "verify_ok": true,
              "verify_stdout": "hello E3\n", "rounds_used": 1 }
}
```

| 字段 | 下游怎么用 |
| --- | --- |
| `environment_id` | **对齐基线用**：检测的基线由 commit 与环境身份共同确定，检测/修复输入直接沿用此值，不要自行命名。环境定义见 4.1 |
| `image_artifact_id` | **起容器用**，指向一条 `IMAGE_REF` 产物，内容就是镜像引用；与环境记录里的 `image` 是同一个编号 |
| `resolved_commit` | **对齐基线用**，检测基线 commit 必须等于它 |
| `dockerfile_artifact_id` | 取 Dockerfile 原文 |
| `iterations[].reason` | **为什么这么改**——环境异常时的首要排查线索 |
| `iterations[].outcome` | `BUILD_OK` / `BUILD_FAILED` / `VERIFY_OK` / `VERIFY_FAILED` |
| `result.build_ok`、`artifact_present` | 第一层：编译通过且产物确实生成 |
| `result.verify_ok` | 第二层：功能验证通过 |

> **下游不要只看 `status`。** 用 `result.verify_ok` 确认环境**真的能跑**，而不只是能编译。
>
> **不变式**：`status = SUCCEEDED` 蕴含 `build_ok`、`artifact_present`、`verify_ok` 均为 `true`，并蕴含 `environment_id` 指向一个可查询的环境。观察到不一致属契约违反。

> **DRAFT 请求里没有 `environment_id`，这是对的。** 它是环境的产出方——环境此时还不存在，输入表达的是「生成要求」（仓库与构建要求），输出才是生成结果。其余三类任务的输入都必须引用已存在的环境。

### 4.1 环境定义：`GET /v1/environments/{environment_id}`

任务里只出现 `environment_id`；完整定义由环境的产出方保存并提供：

```json
{
  "environment_id": "env-draft-fixture-mode0",
  "image": "image-ref-001",
  "project_root": "/workspace/fixtures/draft",
  "working_directory": "/workspace/fixtures/draft",
  "build_command": "make",
  "runtime_capabilities": ["ptrace"]
}
```

| 字段 | 说明 |
| --- | --- |
| `environment_id` | 平台全局唯一的环境身份。它取代了此前的 `configuration_id`——同一环境不再有两个名字 |
| `image` | 引用一条 `IMAGE_REF` 产物（按 `artifact_id`），不内嵌镜像 tag：镜像信息只有一处定义 |
| `project_root` | 代码在**容器内**的位置 |
| `working_directory` | 从哪个目录执行 |
| `build_command` | 该环境约定的构建方式。**任务输入不再重复传构建命令**，v1 也不支持按任务覆盖 |
| `runtime_capabilities` | 执行该环境所需的运行能力（v1 只有 `ptrace`）。**由调用方在生成请求里提出**，环境生成服务固定进环境记录——依赖检测要读文件访问记录，所以检测所用环境必须声明 `ptrace`；这是需求，不是「当前机器有什么能力」。检测任务引用未声明 `ptrace` 的环境会被拒绝 |

四条约定：

1. **环境创建后不可变**：需要改动就新建一个（`env-001` → `env-002`）。就地修改会让下游手里的同一个 ID 指向两种环境。
2. **任务不内嵌环境定义**：检测与修复只传 `environment_id`；内嵌 `image_ref` / `build_command` / `project_subdir` 都会被拒绝。
3. **环境不存在则任务不被受理**：`environment_id` 未登记即 `400`；查询未登记的环境返回 `404`。
4. **环境与仓库正交**：环境回答「在哪里、以什么方式执行」，仓库回答「执行什么代码」，两者由任务同时引用。

> `project_root` 是**容器内**位置，与 DRAFT 输入里的 `build.project_subdir`（**仓库内**相对路径）不是同一个东西：DRAFT 把仓库的对应子目录放进容器，`project_subdir` 决定 `project_root` 取什么值。

## 5. REPAIR：创建任务

`POST /v1/repair-jobs`

```json
{
  "job_type": "REPAIR",
  "trace_id": "trace-repair-0001",
  "input": {
    "repository": { "url": "https://github.com/241880199/DevOps",
                    "commit": "31cd2ad96ad5660db491b41aa2a396e7f1e092a3" },
    "report": {
      "artifact_id": "error-report-003",
      "artifact_uri": "artifact://oracle/job-oracle-mdfixer01/error-report.json",
      "finding_type": "MISSING",
      "commit": "31cd2ad96ad5660db491b41aa2a396e7f1e092a3"
    },
    "environment_id": "env-draft-mdfixer-001",
    "makefile_path": "Makefile",
    "verification": {
      "verify_command": "./app",
      "recheck_command": "make clean && make"
    },
    "limits": { "max_iterations": 3, "timeout_seconds": 300 }
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `input.repository.url` | ✅ | 仓库地址，须可由修复环境克隆（`https://`） |
| `input.repository.commit` | ✅ | **完整 40 位** SHA，不接受缩写：报告里的每条发现都带完整 SHA，版本比对必须逐字符相等。必须与报告所依据的版本一致，否则报告失效（`REPAIR_6001`） |
| `input.report.artifact_id` | ✅ | 问题报告的**全局产物编号**，唯一的取回依据（`GET /v1/artifacts/{artifact_id}`） |
| `input.report.artifact_uri` | ⬜ | 报告的原始地址，只作对照用；填了必须与产物记录里的 `uri` 一致 |
| `input.report.finding_type` | ✅ | **固定 `MISSING`**。请求修复冗余依赖会被拒绝 |
| `input.report.commit` | ⬜ | 报告所依据的版本 SHA，**完整 40 位**（与 `repository.commit` 一致：两者逐字符比对）。**建议填**——填了就在受理阶段比对，不填则要取回报告后才发现不符 |
| `input.environment_id` | ✅ | 修复所依据的环境，由环境生成服务产出。镜像、项目根与构建命令都从该环境读取；报告里的 `location.file` 与 `makefile_path` 相对环境的 `project_root` 解析 |
| `input.makefile_path` | ⬜ | 构建脚本相对项目根的路径，默认 `Makefile` |
| `input.verification.verify_command` | ✅ | 验证修改是否生效，在环境的项目根下执行 |
| `input.verification.recheck_command` | ✅ | 复检依赖问题（通常为重新调用检测服务）。**必填**：输出里的 `recheck_ok` 是「补丁是否真的消除了依赖问题」的唯一依据，不跑复检就无法断言它 |
| `input.limits` | ✅ | 迭代轮数与超时 |

> **报告的不可用情形在受理阶段就被拒绝**（`REPAIR_6001`）：编号取不到、产物不是 `ERROR_REPORT`（拿一份 Dockerfile 或补丁当报告）、报告属于**另一个环境**（不同环境下的依赖结论不可比）、**内容解析不了或不符合 `error-report.schema.json`**（字节坏掉的报告不能驱动一次补丁生成）、**内容与产物记录的 `source_commit` 不一致**（元数据不可信时版本比对就是空转）、报告里**没有 `MISSING` 发现**（没有可修的目标时「修复」无意义）。版本不符则分两处：声明了 `report.commit` 时在受理阶段拒绝，未声明时在执行阶段取回报告后以 `FAILED / REPAIR_6001` 收场。

> **为什么环境改成了引用。** 此前请求里内嵌 `environment{image_ref, build_command, ...}`，与检测侧内嵌 `environment` 是同一类问题：同一份环境约定出现两处副本，两处各自演化后「同一个环境」就有了两个说法。现在构建方式只在环境里表达，任务是引用方。
>
> **验证命令仍留在请求里**，因为环境只回答「在哪里、以什么方式**执行**」，而「这次改动算不算修好」是修复任务自己的判据。

> **`report.commit` 与 `repository.commit` 不一致会发生什么。** 填了 `report.commit` 的话，请求在受理阶段就被 `400` 拒绝（`error.code = REPAIR_6001`），不创建任务；不填的话，任务会创建，执行阶段取回报告后发现不符，任务以 `REPAIR_6001` 失败。两种情形是同一个事实，只是发现得早晚不同。

## 6. REPAIR：输出

```json
"output": {
  "patch_artifact_id": "patch-0001",
  "resolved_commit": "31cd2ad96ad5660db491b41aa2a396e7f1e092a3",
  "fixed": [
    { "target": "main.o", "dependency": "config.h", "style": "TARGET",
      "strategy": "在该目标的依赖列表中直接追加依赖项" }
  ],
  "rejected": [
    { "target": "main.o", "dependency": "unused.h",
      "reason": "候选补丁顺带删除了这条冗余声明。修复只针对缺失依赖，冗余声明的去留由维护者决定，越界改动不予采纳" }
  ],
  "declaration_style_note": "Makefile 使用原子依赖列表，未经宏组织……",
  "verification": { "build_ok": true, "test_ok": true, "recheck_ok": true }
}
```

| 字段 | 说明 |
| --- | --- |
| `patch_artifact_id` | 补丁产物引用。无可采纳补丁时缺失 |
| `fixed[].style` | 原声明风格：`TARGET` 原子列表 / `MACRO` 经宏组织 / `HYBRID` 混合 / `IMPLICIT` 隐式规则 |
| `fixed[].strategy` | 采用的修补手段，供维护者判断改动是否可接受 |
| `rejected[].reason` | **被拒绝的候选及原因**。拒绝不是失败——拒掉一个会引入新问题的候选是正确行为，但必须留痕 |
| `verification.build_ok` | 应用补丁后构建通过 |
| `verification.test_ok` | 功能验证通过且与原行为一致 |
| `verification.recheck_ok` | **复检后原缺失依赖已消失，且未引入新的依赖问题** |

> 三项判据缺一不可。`recheck_ok` 是最关键的一条：补丁改对了位置但没有真正消除问题，与前两项都通过并不矛盾。注意它的措辞是「未**引入**新的依赖问题」——报告里原有的冗余声明若未被动过，不算引入新问题。

> 补丁内的路径以环境的 `project_root` 为基准，与输入报告中 `location` 的基准一致；`fixed[].style` 描述的是**原项目**的声明风格，补丁保持该风格，不重写为另一种。

### 怎么判断这次修复成功了没有

**不要只看 `status`。** 修复服务的成功判据是「给出判断」，不是「产出补丁」，所以两种情形都是 `SUCCEEDED`：

| 情形 | `status` | `output` | 下游怎么理解 |
| --- | --- | --- | --- |
| 产出了可采纳补丁 | `SUCCEEDED` | `fixed` 非空，`verification` 三项为真 | 有补丁可用，取 `patch_artifact_id` |
| **所有候选都被拒绝** | `SUCCEEDED` | `fixed` 为空数组，`rejected` 非空 | **没有补丁可用**，逐条看 `rejected[].reason` 判断是否要人工介入 |
| 报告取不到 / 版本不符 | `FAILED` | — | `error.code = REPAIR_6001`，修复没有可信的输入 |
| 补丁工具跑不起来 | `FAILED` | — | `error.code = REPAIR_6002`，修复过程本身没跑成 |

判据是**「做完判断」与「判断没做成」**：

- `rejected[]` 是**做完判断**的结果——候选被正常评估过，只是结论为「不可接受」。这是产出，必须留痕。
- `REPAIR_6001` / `REPAIR_6002` 是**判断没做成**——输入不可信，或工具跑不起来。

**「全部候选被拒」为什么不判 `FAILED`**：`FAILED` 的任务没有 `output`，`rejected[]` 里那些理由就没地方放了。详见 `docs/ADR/ADR-006` 与 `contracts/error-codes.md` 第 6 节。

### 两条不变式

- `fixed` 非空 ⟹ `verification.build_ok` / `test_ok` / `recheck_ok` 均为 `true`；
- `fixed` 为空 ⟹ `rejected` 非空，且**不带** `patch_artifact_id`。

由 `scripts/validate.py` 检查 08 强制。

## 7. 依赖问题报告契约

检测服务产出、修复服务消费，作为 artifact 交接：任务里只引用 `artifact_id`，取回走 `GET /v1/artifacts/{artifact_id}`。结构见 `contracts/error-report.schema.json`，决策理由见 `docs/ADR/ADR-005`。

```json
{
  "schema_version": "2.0",
  "repository": {
    "url": "https://github.com/241880199/DevOps",
    "canonical_url": "https://github.com/241880199/DevOps",
    "commit": "31cd2ad96ad5660db491b41aa2a396e7f1e092a3"
  },
  "environment_id": "env-draft-mdfixer-001",
  "produced_by": { "detector": "BuildChecker", "job_id": "job-full01", "mode": "FULL" },
  "generated_at": "2026-09-20T09:40:00.000Z",
  "summary": { "missing": 1, "redundant": 0 },
  "findings": [
    {
      "type": "MISSING",
      "target": "main.o",
      "dependency": "config.h",
      "commit": "31cd2ad96ad5660db491b41aa2a396e7f1e092a3",
      "detector": "BuildChecker",
      "provenance": "TOOL",
      "location": { "file": "Makefile", "line": 9,
                    "detail": "main.o 的依赖列表为 main.c unused.h，未含 config.h" },
      "evidence": { "kind": "FILE_ACCESS", "detail": "构建 main.o 期间读取了 config.h" }
    }
  ]
}
```

> 上面是**工具产出**的报告；本仓库另有一份**人工标准答案**报告（`fixtures/mdfixer/error-report.json`，三条发现、`provenance` 全为 `INSTRUCTOR_ORACLE`），供修复任务在真实检测结果到位前有确定输入。两份报告的 `commit` 与 `environment_id` 都指向同一版本与同一环境。

### 两条容易忽略的约定

**每条发现必须同时带 `location` 与 `evidence`。** 光有 `(target, dependency)` 无法复核——复核者不知道去哪一行确认，也不知道判定依据。缺任一者报告不可复核。

**`provenance` 显式区分工具与人工来源。** `detector` 说明是**哪个**工具，`provenance` 说明是哪**一类**来源（`TOOL` / `INSTRUCTOR_ORACLE` / `MANUAL`）。消费方过滤人工样本时判断枚举值即可，不必猜测检测器的命名约定——靠字符串约定会让统计静默失真。

报告**可以同时包含** `MISSING` 与 `REDUNDANT`（如实反映检测结果）；修复请求把范围限定为 `MISSING`，边界在请求侧收窄，而不是在报告侧裁剪。

## 8. 错误码与状态语义

### 状态机

```
QUEUED ──> RUNNING ──┬──> SUCCEEDED    结果可用，output 必填，不得携带 error
   │                 ├──> FAILED       error 必填
   │                 └──> TIMED_OUT    error 必填
   └─────────────────> CANCELLED       error 必填
```

- `output` 与 `error` **只在终态出现**：`QUEUED` / `RUNNING` 阶段只返回任务元数据。
- 终态一经到达不再变更。

> **为什么执行中不回传部分结果。** 若允许 `RUNNING` 携带部分 `output`，消费方就要同时处理两种输出形状，字段必填性也会随状态浮动，schema 无法静态约束。理由见 `docs/ADR/ADR-004`。

### 错误码

| 错误码 | 含义 | 下游应如何反应 |
| --- | --- | --- |
| `ENV_3002` | 镜像构建失败 | 环境不可用。**不要**在缺环境的情况下继续检测 |
| `EXEC_4002` | 任务超时 | 可考虑放宽 `limits.timeout_seconds` 后重试 |
| `ANALYSIS_5001` | 分析器失败 | 由检测服务产出 |
| `REPAIR_6001` | 修复输入不可用：报告取不到 / 不符合契约 / 版本与请求不符 | 修复没有可信的输入。重新取报告或修正 `repository.commit` 后再提交，**不要**原样重试 |
| `REPAIR_6002` | 修复过程无法进行：缺补丁工具、工作副本不可写 | 环境问题（通常是 `image_ref` 里缺 `git`/`patch`），修环境后重试 |

### 受理阶段拒绝的载体

请求本身不合法时，任务不会被创建：HTTP `400`，响应体为 `{ "error": { "code", "message", "at" } }`。
字段校验失败、必填缺失、`job_type` 与端点不符、路径越界、引用未登记的环境等都走这条路径。

`code` 取共享错误码表里的值，但**共享表目前没有「请求不合法 / 输入不可用」这一档**：5 个码分别描述执行期故障
（`ENV_3002` / `EXEC_4002` / `ANALYSIS_5001` / `REPAIR_6001` / `REPAIR_6002`），没有一个表达「受理时就发现请求不对」。
本地实现暂用 `EXEC_4002` 承载这一档，语义并不精确——**已列为待双方在共享错误码表里补一档的缺口**，
补上之后只需要替换载体，不影响任何字段结构。

同一档缺口还包括两种具体的输入问题：**环境生成请求里的版本无法解析为真实提交**（同样在受理阶段拒绝），
以及**环境不存在**（查询返回 `404`）。三处都缺一个语义准确的码。

### 最关键的一条

**「发现问题」不等于「执行失败」。**

检出缺失依赖说明检测服务**正常完成了工作**，任务终态是 `SUCCEEDED`，发现写入报告产物，**不是** `error`。把「发现 MD」写成 `FAILED` 会让调度器把成功分析当故障重试。

对环境生成：某一轮候选构建失败但已定位原因、继续迭代，属于过程状态，记入 `iterations[].outcome`，**不写入** `job.error`。

对修复：候选被评估后判定不可接受（`rejected[]`）同样是过程状态，不影响任务终态——**即使所有候选都被拒绝**，任务仍是 `SUCCEEDED`。真正写入 `job.error` 的只有 `REPAIR_6001` 与 `REPAIR_6002` 两种「判断没做成」的情形。

### 自检三问

接入方在联调前应确认对以下三问答案一致：

1. 检测服务报告了一条 MD，这个 job 的 `status` 是什么？ → **`SUCCEEDED`**
2. 分析进程段错误崩溃了，这个 job 的 `status` 是什么？ → **`FAILED`**，`error.code = ANALYSIS_5001`
3. 修复服务把所有候选补丁都拒了，这个 job 的 `status` 是什么？ → **`SUCCEEDED`**，`output.fixed` 为空、`output.rejected` 非空

## 9. 产物访问

产物以 URI 引用交接，不内嵌进响应（见 `docs/ADR/ADR-002`）。

```json
{
  "artifact_id": "dockerfile-001",
  "type": "DOCKERFILE",
  "uri": "artifact://draft/job-draft01/Dockerfile",
  "media_type": "text/x-dockerfile",
  "producer_job_id": "job-draft01",
  "environment_id": null,
  "sha256": "3d25c855c116dc8cd0101b2851586d9895f11f0f978f34fca47ff7d0a1a26bcf",
  "size_bytes": 519,
  "created_at": "2026-09-20T10:03:41.000Z",
  "source_commit": "d47a1523beec3311033eabf2e74c2a6ac299720d"
}
```

修复服务产出的补丁同理：

```json
{
  "artifact_id": "patch-0001",
  "type": "PATCH",
  "uri": "artifact://mdfixer/job-repair01/fix.patch",
  "media_type": "text/x-diff",
  "producer_job_id": "job-repair01",
  "environment_id": "env-draft-mdfixer-001",
  "sha256": "b6e14fa1c8d34d93614a279db5c0e36515bdc113fb1cc403c83505017d8fd561",
  "size_bytes": 199,
  "created_at": "2026-09-20T11:01:47.000Z",
  "source_commit": "31cd2ad96ad5660db491b41aa2a396e7f1e092a3"
}
```

| 字段 | 约定 |
| --- | --- |
| `type` | 八类，产出方矩阵见共享契约：`DOCKERFILE` / `BUILD_LOG` / `VERIFY_LOG` / `IMAGE_REF` 由环境生成服务产出；`ACTUAL_GRAPH` / `DECLARED_GRAPH` 只由全量检测产出；`ERROR_REPORT` 由两类检测产出；`PATCH` 由修复服务产出 |
| `uri` | 存储域**按服务命名**：`draft` / `mdfixer` / `buildchecker` / `echecker`；**人工基线样例**用 `oracle` 域，以免冒充工具产出。取值集合由校验钉死，新增域必须先写进契约与文档 |
| `environment_id` | 该产物所属的环境。**环境生成服务自己的产物一律为 `null`**——它们产出时环境尚不存在；其余产物必须记录所属环境 |
| `sha256` / `size_bytes` | 内容完整性。记录值必须是实物的真实摘要，由 `scripts/validate.py` 检查 06 逐字节核验 |
| `created_at` | 产物**成功持久化并可引用**的时间，UTC 毫秒精度 |
| `source_commit` | 八类一律必填：产物所针对的源码版本 |

样例中的 `sha256` 都取自仓库里真实存在的文件（`fixtures/draft/docker/Dockerfile.ok`、
`fixtures/draft/docker/image-ref.txt`、`fixtures/mdfixer/reference.patch`、
`fixtures/mdfixer/docker/image-ref.txt`、`fixtures/mdfixer/error-report.json`）。
文件改一个字符，校验就会失败——**摘要不实的产物记录比没有摘要更危险**，
它会让下游的完整性核验变成走过场。

**取用方式已定：一律调用 `GET /v1/artifacts/{artifact_id}`。** 产物按全局编号定位，
`uri` 是给人看的原始地址，不承担寻址职责——此前「本地路径映射」与「下载接口」二选一的
悬置状态就此结束。`sha256` 用于核验内容完整，`source_commit` 保证产物可追溯到它产出的源码版本。

## 10. 检测类任务契约

`FULL_CHECK` 与 `INCREMENTAL_CHECK` 由依赖检测服务负责。以下内容已对齐 `contract-phase@431a743` 的公共结构，但仍是第二阶段接口提案，须在 `contract-phase/interfaces/` 经双方确认后冻结。

### FULL_CHECK

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `repository.url` | ✅ | 调用方原始仓库地址，原样保留 |
| `repository.canonical_url` | ✅ | 按平台规则规范化的 HTTPS 地址 |
| `repository.commit` | ✅ | 完整 40 位 SHA，不接受缩写、分支名或标签 |
| `environment_id` | ✅ | 平台全局环境 ID；镜像、项目根和构建命令不再内嵌于任务 |

> 检测样例引用的 `env-draft-fixture-mode0` 就是环境生成服务的样例环境
> （`contracts/samples/environment.draft-fixture-mode0.json`）：它声明了 `ptrace` 运行能力，
> 因为检测要读文件访问记录。环境不存在时任务不被受理。

### INCREMENTAL_CHECK

在 FULL_CHECK 基础上增加：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `base_commit` | ✅ | 基线的完整 SHA |
| `baseline.actual_graph_artifact_id` | ✅ | BuildChecker 基线实际图的全局 Artifact ID |
| `baseline.commit` | ✅ | 应**等于** `base_commit`，不一致时任务被拒绝 |
| `baseline.environment_id` | ✅ | 应与本次 `environment_id` 一致，不一致时结果不可比 |

**历史图必须能追溯到 base commit 和环境。** 基线只传 Artifact ID，不传逻辑 URI；调用方通过统一下载接口取用。

### FULL_CHECK 输出

权威文件：`contracts/job-output-full-check.schema.json`。

输出包含 `resolved_commit`、`environment_id`、实际依赖图、声明依赖图和错误报告的产物编号，以及 MD/RD 汇总。图文件遵循 `contracts/dependency-graph.schema.json`，报告遵循 `contracts/error-report.schema.json`。同步说明见 ADR-010。

### INCREMENTAL_CHECK 输出

权威文件：`contracts/job-output-incremental-check.schema.json`。

输出同时保留 `base_commit`、当前 `resolved_commit` 与 `environment_id`，返回当前错误报告，并在 `changes.added` 与 `changes.resolved` 中表达相对基线的变化。按照共享产出方矩阵，EChecker **不产出 `ACTUAL_GRAPH`**；实际图仅由 BuildChecker 产出。同步说明见 ADR-010。

## 11. 版本与变更政策

四类任务当前统一使用 Job `schema_version=2.0`。从本地旧结构迁移到 `contract-phase` 公共结构
包含字段删除、改名和语义变化（`configuration_id` → `environment_id`、环境定义不再内嵌、
修复的路径基准从 `project_subdir` 改为环境的 `project_root`），因此不能继续沿用 `1.0`。

DRAFT / REPAIR 的迁移与检测侧同步完成：本地样例已全部升级为 2.0，旧结构只作为历史记录保留在
`contracts/task-legacy-v1.schema.json` 与 `docs/ADR/ADR-007`、`docs/接口说明.md` 第 16 节，
不再有任何样例引用。迁移方案与理由见 `docs/ADR/ADR-011`。

| 变更类型 | 例子 | 兼容性 |
| --- | --- | --- |
| 兼容 | 新增**可选**字段 | 消费者须允许未知字段；共享 schema 同步更新 |
| 破坏 | 字段删除、改名、改语义；`status` 或 `job_type` 枚举取值变动 | 必须递增 `schema_version`，双方同步升级 |

`status` 枚举一旦变更，所有消费方的分支逻辑都会失效，属最高风险变更。
