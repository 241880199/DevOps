# 接口说明

面向**下游消费方**（依赖检测服务、依赖修复服务）的对接文档。

环境生成服务（`job_type: DRAFT`）接收一个仓库，产出一个**能成功构建并可运行**的 Dockerfile 与镜像引用，供下游在该环境中执行构建、检测与修复。

- 契约权威来源：`contracts/*.schema.json`
- 错误语义详解：`contracts/error-codes.md`
- 可执行校验：`python scripts/validate.py`

---

## 1. 交接什么

### 1.1 本服务交给下游

| 交接物 | 字段 | 下游用途 |
| --- | --- | --- |
| 可运行镜像 | `output.image_ref` | 起容器，在其中执行全量/增量构建 |
| Dockerfile | `output.dockerfile_artifact_id` → 产物 | 需要重建、审查或复现环境时取用 |
| 实际使用的版本 | `output.resolved_commit` | **对齐基线**：检测所依据的 commit 必须与此一致 |
| 每轮迭代记录 | `output.iterations[]` | 排查「环境为什么是这样搭的」 |
| 构建与验证结论 | `output.result` | 判断环境是否真的可用，而非仅「构建通过」 |

### 1.2 本服务需要下游提供

| 需要你方明确 | 说明 |
| --- | --- |
| 版本对齐 | 你方检测所依据的 commit，必须与我方 `output.resolved_commit` 一致。不一致时结果不可比 |
| 环境有效性判据 | 若你方除「能构建」外还要求「能运行测试」，请在创建任务时通过 `build.verify_command` 与 `build.verify_expect` 表达 |
| 是否需要 `configuration_id` | 见第 11 节待确认事项——我方当前输出**不包含**该字段 |
| 产物读取方式 | 你方以本地路径映射还是调用下载接口取产物，需双方事先约定（见第 6 节） |

## 2. 端点

| 操作 | 方法与路径 | 说明 |
| --- | --- | --- |
| 生成构建环境 | `POST /v1/dockerfile-jobs` | 受理后立即返回 `202`，不等待执行 |
| 查询任务 | `GET /v1/jobs/{job_id}` | 查询状态、结果或错误 |
| 下载产物 | `GET /v1/artifacts/{artifact_id}` | 返回产物原始字节 |

任务采用**异步模型**：创建只做受理，执行在后台进行。理由见 `docs/ADR/ADR-001`。

## 3. 创建任务

### 请求

`POST /v1/dockerfile-jobs`，`Content-Type: application/json`

```json
{
  "job_type": "DRAFT",
  "trace_id": "trace-draft-0001",
  "input": {
    "repository": {
      "url": "https://github.com/241880199/DevOps",
      "commit": "b06e66e"
    },
    "build": {
      "command": "make",
      "verify_command": "./hello",
      "verify_expect": "hello draft"
    },
    "limits": { "max_iterations": 5, "timeout_seconds": 600 },
    "context_documents": ["README.md"]
  }
}
```

### 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `job_type` | ✅ | 固定 `DRAFT`。未知取值一律拒绝 |
| `trace_id` | ⬜ | 透传的追踪号，用于串联同一次平台流程 |
| `input.repository.url` | ✅ | 仓库地址 |
| `input.repository.commit` | ⬜ | 建议给**完整** SHA。缺失时取默认分支 HEAD，并在 `output.resolved_commit` 回报实际值 |
| `input.build.command` | ✅ | **第一层判据**：构建命令，退出码 0 且产物存在才算通过 |
| `input.build.verify_command` | ✅ | **第二层判据**：功能验证命令 |
| `input.build.verify_expect` | ⬜ | 期望输出，用于自动比对；缺失时只校验退出码 |
| `input.limits.max_iterations` | ✅ | 最多迭代轮数，1–20 |
| `input.limits.timeout_seconds` | ✅ | 单次构建墙钟上限（秒） |
| `input.context_documents` | ⬜ | 供生成时读取的项目文档，**最多 2 个** |

> **`job_id` 不得出现在请求中**——它由服务端产生。携带即为非法，会被拒绝。

### 响应 `202 Accepted`

```json
{
  "job_id": "job-draft01",
  "job_type": "DRAFT",
  "status": "QUEUED",
  "trace_id": "trace-draft-0001",
  "created_at": "2026-09-20T10:00:00Z"
}
```

拿到 `job_id` 后轮询查询接口。**`202` 表示已受理，不表示已完成。**

## 4. 查询任务

`GET /v1/jobs/{job_id}` → `200 OK`

### 状态机

```
QUEUED ──> RUNNING ──┬──> SUCCEEDED    结果可用，output 必填，不得携带 error
   │                 ├──> FAILED       error 必填
   │                 └──> TIMED_OUT    error 必填
   └─────────────────> CANCELLED       error 必填
```

- `output` 与 `error` **只在终态出现**：`QUEUED` / `RUNNING` 阶段只返回任务元数据，两者皆不得携带。
- 终态一经到达不再变更。

> **为什么执行中不回传部分结果。** 若允许 `RUNNING` 携带部分 `output`，消费方就要同时处理「部分输出」与「完整输出」两种形状，`result`、`iterations` 等字段的必填性也会随状态浮动。代价是消费方在任务结束前看不到中间进展——目前认为这个取舍值得，若确有需要可在后续版本中重新评估。

### 成功结果

```json
{
  "schema_version": "1.0",
  "job_id": "job-draft01",
  "job_type": "DRAFT",
  "status": "SUCCEEDED",
  "execution": { "created_at": "...", "started_at": "...", "finished_at": "...", "attempt": 1 },
  "input": { "...": "原样回显" },
  "output": {
    "dockerfile_artifact_id": "dockerfile-001",
    "image_ref": "draft-fixture-ok:1.0",
    "resolved_commit": "b06e66ec9f3d2a1b4c5e6f708192a3b4c5d6e7f8",
    "iterations": [
      { "round": 0, "action": "INITIAL", "reason": "...", "outcome": "BUILD_OK", "build_log_artifact_id": "buildlog-0001" },
      { "round": 1, "action": "PATCH", "reason": "...", "outcome": "VERIFY_OK", "build_log_artifact_id": "buildlog-0002" }
    ],
    "result": {
      "build_ok": true,
      "artifact_present": true,
      "verify_ok": true,
      "verify_stdout": "hello draft\n",
      "rounds_used": 1
    }
  }
}
```

### 输出字段

| 字段 | 类型 | 下游怎么用 |
| --- | --- | --- |
| `output.image_ref` | string | **起容器用**。这是可直接 `docker run` 的镜像引用 |
| `output.resolved_commit` | string | **对齐基线用**。你的检测基线 commit 必须等于它 |
| `output.dockerfile_artifact_id` | string | 取 Dockerfile 原文，用于审查或重建 |
| `output.iterations[].round` | int | 轮次序号，从 0 起 |
| `output.iterations[].action` | enum | `INITIAL` 初次生成 / `PATCH` 修复 / `OPTIMIZE` 瘦身 |
| `output.iterations[].reason` | string | **为什么这么改**。环境异常时的首要排查线索 |
| `output.iterations[].error_excerpt` | string | 触发本轮修改的日志片段 |
| `output.iterations[].outcome` | enum | `BUILD_OK` / `BUILD_FAILED` / `VERIFY_OK` / `VERIFY_FAILED` |
| `output.result.build_ok` | bool | 第一层：构建命令退出码为 0 |
| `output.result.artifact_present` | bool | 第一层：产物确实生成 |
| `output.result.verify_ok` | bool | 第二层：功能验证通过 |
| `output.result.verify_stdout` | string | 功能验证的实际输出 |
| `output.result.rounds_used` | int | 实际消耗轮数 |

> **不变式**：`status = SUCCEEDED` 蕴含 `build_ok`、`artifact_present`、`verify_ok` 均为 `true`。若观察到不一致，属契约违反，请报缺陷。
>
> **下游不要只看 `status`。** 用 `result.verify_ok` 确认环境**真的能跑**，而不只是能编译——「编译通过但运行结果不对」在实践中是常态。

### 失败结果

```json
{
  "status": "FAILED",
  "error": {
    "code": "ENV_3002",
    "stage": "ENV",
    "message": "镜像构建失败：基础镜像缺少 C 工具链，make 不可用。",
    "detail": "step 5/7 RUN make 退出码 127；日志末尾：/bin/sh: 1: make: not found",
    "at": "2026-09-20T10:05:19Z"
  }
}
```

## 5. 错误码

完整语义见 `contracts/error-codes.md`。要点：

| 错误码 | 含义 | 下游应如何反应 |
| --- | --- | --- |
| `ENV_3002` | 镜像构建失败 | 环境不可用。**不要**在缺环境的情况下继续检测 |
| `EXEC_4002` | 任务超时 | 可考虑放宽 `limits.timeout_seconds` 后重试 |
| `ANALYSIS_5001` | 分析器失败 | 本服务**不产生**此码；由检测服务自身产出 |

### 最关键的一条

**「发现问题」不等于「执行失败」。**

对检测服务：检出缺失依赖说明它**正常完成了工作**，任务终态是 `SUCCEEDED`，发现写入报告产物，**不是** `error`。把「发现 MD」写成 `FAILED` 会让调度器把成功分析当故障重试。

对 DRAFT：某一轮候选构建失败但已定位原因、继续迭代，属于过程状态，记入 `iterations[].outcome`，**不写入** `job.error`。

## 6. 产物访问

产物以 URI 引用交接，不内嵌进响应（理由见 `docs/ADR/ADR-002`）。

```json
{
  "artifact_id": "dockerfile-001",
  "type": "DOCKERFILE",
  "uri": "artifact://draft/job-draft01/Dockerfile",
  "media_type": "text/x-dockerfile",
  "producer_job_id": "job-draft01",
  "sha256": "4120822b...5846",
  "size_bytes": 539,
  "source_commit": "b06e66ec..."
}
```

**双方必须事先约定 URI 的解析方式**，二选一：

1. **本地路径映射**——`artifact://<存储域>/<job_id>/<文件名>` 映射到约定的本地目录；
2. **调用下载接口**——`GET /v1/artifacts/{artifact_id}` 取原始字节。

只给出 URI 而不约定解析方式，等于没有交接。`sha256` 用于核验内容完整，`source_commit` 保证产物可追溯到它产出的源码版本。

## 7. 版本与变更政策

`schema_version` 当前为 `1.0`。

| 变更类型 | 例子 | 兼容性 |
| --- | --- | --- |
| 兼容 | 新增**可选**字段 | 消费者须允许未知字段；共享 schema 同步更新 |
| 破坏 | 字段删除、改名、改语义；`status` 或 `job_type` 枚举取值变动 | 必须递增 `schema_version`，双方同步升级 |

保留已有字段的含义。`status` 枚举一旦变更，所有消费方的分支逻辑都会失效，属最高风险变更。

## 8. 联调检查清单

对接前逐条确认：

- [ ] `JobCreateRequest` 校验通过，`job_id` 不出现在请求中
- [ ] 未知 `job_type` 被拒绝（试着传 `ABC`）
- [ ] 删除 `input.build.command` 被拒绝
- [ ] 删除 `input.limits` 被拒绝
- [ ] `POST` 返回 `202` + `QUEUED`，而非等待到完成
- [ ] 能观察到 `QUEUED → RUNNING → SUCCEEDED` 状态迁移
- [ ] `SUCCEEDED` 的任务不带 `error`；`FAILED` 的任务带 `error`
- [ ] `QUEUED` / `RUNNING` 的任务既无 `output` 也无 `error`
- [ ] 能依 `output.image_ref` 起容器并执行构建
- [ ] 能依 `output.dockerfile_artifact_id` 取到 Dockerfile 原文
- [ ] 双方对「检出依赖问题不等于执行失败」理解一致

自动校验：`python scripts/validate.py`（40 项）。

## 9. 完整走查

```bash
# 1. 创建任务
curl -s -X POST http://127.0.0.1:8080/v1/dockerfile-jobs \
     -H 'Content-Type: application/json' \
     -d @contracts/samples/create-dockerfile-job.request.json
# -> 202 {"job_id":"job-xxxx","status":"QUEUED",...}

# 2. 轮询状态
curl -s http://127.0.0.1:8080/v1/jobs/job-xxxx
# -> {"status":"RUNNING",...}  再查 -> {"status":"SUCCEEDED","output":{...}}

# 3. 取产物
curl -s http://127.0.0.1:8080/v1/artifacts/dockerfile-xxxx
# -> Dockerfile 原文
```

本地可用 `python scripts/mock_server.py --port 8080` 起一个参考实现验证上述流程。

## 11. 待确认事项

以下问题需要消费方拍板，我方据以调整契约：

1. **是否需要 `configuration_id`。** 检测服务描述其输入时需要「可运行镜像 + `configuration_id`」，而环境生成服务的输出**当前不含该字段**。请明确：该标识由谁产生、含义是什么、是否需要我方在 `output` 中回报。
2. **产物 URI 的解析方式**：本地路径映射还是下载接口（见第 6 节）。
3. **`image_ref` 的获取渠道**：当前为本地镜像引用。若下游在不同主机上执行，需要改为镜像仓库地址——请确认是否需要。
4. **是否需要构建产物本身**（可执行文件、中间目标文件），而非仅镜像。当前只交付镜像与 Dockerfile。
