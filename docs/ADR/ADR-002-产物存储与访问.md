# ADR-002：产物通过 URI 引用交接，不内嵌进任务响应

- **状态**：已采纳
- **日期**：2026-09-20

## Context

任务执行会产出大量附件：Dockerfile、每一轮的完整构建日志、功能验证输出、依赖图 JSON、修复补丁。这些产物的规模差异极大：

| 产物 | 典型规模 |
| --- | --- |
| Dockerfile | 数百字节 ~ 数 KB |
| 单轮构建日志 | 数十 KB ~ 数 MB |
| 依赖图 JSON | 数 MB ~ 数十 MB |
| 镜像 | 数百 MB（不可能放进 JSON） |

这些产物需要**跨服务交接**：环境生成服务产出的镜像与构建方案要交给依赖检测服务；依赖检测服务产出的错误报告要交给依赖修复服务。

于是有两种设计选择：把产物内容直接放进任务响应里，还是只放引用、内容另行存取。

## Decision

**任务响应只承载元数据与结构化的小结果；大产物一律以 URI 引用交接。**

产物记录的结构（见 `contracts/artifact.schema.json`）：

```json
{
  "artifact_id": "dockerfile-001",
  "type": "DOCKERFILE",
  "uri": "artifact://draft/job-draft01/Dockerfile",
  "media_type": "text/x-dockerfile",
  "producer_job_id": "job-draft01",
  "sha256": "3d25c855...26bcf",
  "size_bytes": 519,
  "source_commit": "d47a1523beec3311033eabf2e74c2a6ac299720d"
}
```

配套约定：

1. **URI 形如 `artifact://<存储域>/<job_id>/<文件名>`**，接收方**必须事先约定解析方式**——本地路径映射，或调用下载接口。仅给出 URI 而不约定解析方式，等于没有交接。
2. **读取接口**：`GET /v1/artifacts/{artifact_id}`，返回原始字节，`Content-Type` 取自记录的 `media_type`。
3. **完整性与可追溯**：`sha256` 用于交接时核验内容未被篡改或截断；`producer_job_id` 与 `source_commit` 保证任一产物都能回溯到「哪个任务、在哪个源码版本上」产出的。

## Alternatives

| 方案 | 优点 | 为何不选 |
| --- | --- | --- |
| **内嵌进任务响应** | 一次请求拿全，实现最简单，无额外接口 | 数 MB 的日志与数十 MB 的依赖图会让响应体膨胀到不可用；镜像根本放不下；且每次查询任务都要重复传输全部附件 |
| **只给本地文件路径** | 零额外基础设施 | 跨服务、跨容器时路径不成立；无法表达「哪个存储域」；不便于后续换后端 |
| **对象存储直连（S3/OSS）** | 成熟、可扩展、天然支持大文件 | 引入外部依赖与凭据管理；当前产物规模与访问模式尚不需要。URI 方案不排除后续把解析落到对象存储上 |
| **数据库 BLOB 字段** | 事务一致 | 大字段读写放大数据库压力，备份与迁移成本高 |

## Consequences

**正面**

- 任务响应体保持小而稳定，查询接口的延迟与产物规模解耦。
- 产物可以独立于任务被访问、缓存、校验。
- 存储后端可替换：改的是 URI 的解析实现，不是契约本身。

**代价**

- **多一次交互**：接收方拿到 URI 后需要再发一次请求取内容。
- **必须额外实现下载接口**与 `artifact_id` 的唯一性管理。
- **引用可能失效**：产物被清理后 URI 仍存在，接收方需要处理「引用有效但内容缺失」的情况。
