# ADR-006：修复失败的边界，与报告版本一致性

- **状态**：已采纳
- **日期**：2026-09-20
- **相关契约**：`contracts/job-input-repair.schema.json`、`contracts/job-output-repair.schema.json`、`contracts/error-codes.md` 第 6 节

## Context

ADR-003 把「发现问题」与「执行失败」分开表示，当时给出的修复侧例子只有一句：

> 对修复：候选被拒绝（`rejected[]`）同样是过程状态，不影响任务终态。

这句话在**部分候选**被拒时成立，但把边界留在了灰区。B 组在检查修复交接时遇到三个具体问题：

1. **全部候选都被拒绝时，任务是什么终态？** 说 `SUCCEEDED` 的理由是「修复服务正常完成了工作」；说 `FAILED` 的理由是「这次修复没有产出任何补丁」。两种说法都通，不写死就会出现两套实现。

2. **`FAILED` 的任务没有 `output`。** 如果「全部候选被拒」判为 `FAILED`，那么 `rejected[]` 里逐候选的理由就没地方放——而这些理由是修复服务唯一有价值的产出。判据不能只看状态语义，还得看**信息放在哪里**。

3. **报告属于哪个源码版本，此前无法在受理阶段判断。** `contracts/job-input-repair.schema.json` 里写着「报告必须与请求的 `repository.commit` 一致，否则报告失效」，但请求只给报告的 `artifact_uri`。服务端必须**先取回报告**才知道版本对不对——若不符，是一次白跑的调度：任务创建、排队、起容器，最后才发现输入根本不可用。

这三条都落在修复服务自己身上，因此由 B 组在 E2 阶段定稿。

## Decision

### 一、修复的成功判据是「给出判断」，不是「产出补丁」

| 情形 | 存放位置 | 任务终态 | 错误码 |
| --- | --- | --- | --- |
| 部分候选被采纳，部分被拒 | `output.fixed` + `output.rejected` | `SUCCEEDED` | 无 |
| **全部候选都被拒绝** | `output.fixed = []` + `output.rejected` 非空 | **`SUCCEEDED`** | 无 |
| 报告取不到 / 不符合契约 / 版本与请求不符 | `job.error` | `FAILED` | `REPAIR_6001` |
| 补丁生成或应用本身跑不动（缺工具、副本不可写） | `job.error` | `FAILED` | `REPAIR_6002` |

界线是**「做完判断」与「判断没做成」**：

- `rejected[]` 是**做完判断**的结果。候选被正常评估过，结论是「不可接受」。这是产出，必须逐条留痕。
- `REPAIR_6001` / `REPAIR_6002` 是**判断没做成**。输入不可信，或工具跑不起来，此时连一条可信的候选结论都拿不出来。

### 二、由此得到的两条不变式

- `output.fixed` 非空 ⟹ `verification` 的 `build_ok` / `test_ok` / `recheck_ok` 三项均为 `true`；
- `output.fixed` 为空 ⟹ `output.rejected` 非空，且**不带** `patch_artifact_id`。

第二条是新增的。原先把「至少修复一处」当作成功修复任务的固定特征，这在「全部被拒」时自相矛盾——而那种情形是合法且常见的。第二条不是放松要求：它把「没产出补丁」从「未定义行为」变成了「必须给出理由」，比原先更严。

### 三、`report.commit` 进请求，让版本校验前移到受理阶段

`job-input-repair.schema.json` 的 `report` 增加**可选**字段 `commit`：

- **填了**：受理时直接与本请求的 `repository.commit` 比对，不一致以 `400` 拒绝，`error.code = REPAIR_6001`，不创建任务。
- **不填**：服务端取回报告后校验其 `repository.commit`，不一致或报告取不到时任务以 `REPAIR_6001` 失败。

同一个错误码出现在两个位置（受理拒绝、执行失败），这不是不一致——版本不符是同一个事实，只是发现得早晚不同；早发现发生在 HTTP 层，晚发现发生在任务层。

字段选**可选**而非必填，是因为必填会破坏现有调用方（`report` 对象是 `additionalProperties: false`）。加可选字段是兼容变更（见 `docs/接口说明.md` 第 11 节），A 组可以立即开始填，也可以先不填。

### 四、`project_subdir` 补上，否则报告里的路径无从解析

报告里 `location.file` 写的是 `Makefile`——相对哪一个根？请求里 `makefile_path` 同样。仓库根就是项目根时无所谓，但本仓库自己就不是（可构建的样例在 `fixtures/draft/`、`fixtures/mdfixer/`）。因此修复输入增加可选的 `project_subdir`，与 DRAFT 输入的同名字段保持一致的语义：**项目根相对仓库根的路径，默认为 `.`**。

## Alternatives

| 方案 | 优点 | 为何不选 |
| --- | --- | --- |
| **全部候选被拒 → `FAILED`** | 状态一眼看出「这次没修成」 | `FAILED` 没有 `output`，`rejected[]` 的理由无处安放；且会诱导调度器重跑一次已经得出确定结论的昂贵任务 |
| **全部候选被拒 → `SUCCEEDED`，但新增 `outcome: "NO_FIX"` 字段** | 状态之外多一个显式标记 | 与 `fixed` 是否为空表达同一件事，两个字段会漂移；消费者要同时看两处 |
| **`report.commit` 设为必填** | 版本一致性 100% 可在受理阶段判定 | 破坏兼容：现有请求全部失效，需递增 `schema_version`。E2 阶段不值当 |
| **版本校验只留在执行阶段** | 不改契约 | 报告版本不符是**可静态判定**的事实，拖到执行阶段等于故意浪费一次容器调度 |
| **让检测方在报告 URI 里编入 commit**（如 `artifact://…/<commit>/report.json`） | 不新增字段 | 靠 URI 格式约定传语义，脆弱且隐式——正是 ADR-005 明确拒绝过的做法（`provenance` 那条） |

## Consequences

**正面**

- 「全部候选被拒」有了唯一确定的表示，两个小组不会各写一套。
- 报告版本不符在受理阶段就能拦下，省掉一次白跑的调度。
- `rejected[]` 的理由在任何情况下都有地方存放——这是修复报告可复核的前提。

**代价**

- 消费方判断「修复成功了没有」不能只看 `status`，还要看 `output.fixed` 是否为空。这一点写进 `docs/接口说明.md` 第 6 节与 `contracts/error-codes.md` 的自检第 3 问。
- `REPAIR_6001` 同一个码出现在 HTTP 层与任务层两种载体上，消费方两侧都要处理。
- `project_subdir` 默认 `.`，既有调用方不受影响，但**默认为根**意味着非根项目若忘了填，症状是「补丁上下文对不上」而不是「路径找不到」——较难定位。这一点在字段描述里写明。
