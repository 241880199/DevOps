# ADR-001：耗时操作采用异步任务模型

- **状态**：已采纳
- **日期**：2026-09-20

## Context

平台上的四类操作（生成构建环境、全量依赖检测、增量依赖检测、依赖修复）有一个共同的物理特征：**执行时间远超 HTTP 请求的合理生命周期**。

- 拉取仓库、构建镜像、跑一次全量构建，动辄数十秒到数十分钟；
- 一次依赖检测可能要执行多轮构建；
- 调用方与执行方通常是**不同的服务、不同的人**，需要跨进程取结果。

如果采用同步 HTTP——请求发出后一直挂起等待结果——会同时引入四个问题：

1. **连接生命周期不可控**：网关、代理、客户端任一侧超时都会中断请求，但后台的构建**仍在继续**，结果丢失且无人知晓。
2. **客户端与执行深度耦合**：客户端必须全程在线，断线即失败。
3. **无法查询进度**：调用方只能知道「最终成功或失败」，看不到中间状态，出了问题没法排查。
4. **无法幂等重试**：超时后重发请求，会重复触发昂贵的构建。

## Decision

**所有耗时操作一律建模为异步任务（Job）**，采用「提交—轮询」两段式：

```
POST /v1/<kind>-jobs   ->  202 Accepted  { job_id, status: "QUEUED" }
GET  /v1/jobs/{job_id} ->  200 OK        { ..., status, output|error }
```

- 创建接口只做**受理**：校验请求、落库、立即返回 `202` 与 `job_id`，**不等待执行**。
- 四类任务共用一个任务查询接口 `GET /v1/jobs/{job_id}`，共用一个任务模型（见 `contracts/task.schema.json`）。
- 状态机为 `QUEUED → RUNNING → 终态`，终态一次到达不再变更。
- 执行在后台进行，任务元数据持久化，进程重启后仍可查询。

## Alternatives

| 方案 | 优点 | 为何不选 |
| --- | --- | --- |
| **同步等待** | 实现最简单，无任务存储、无状态机 | 客户端与执行耦合；超时后任务状态不可知；无法查询进度。上述四个问题一个都绕不开 |
| **回调 / Webhook** | 无需客户端轮询，实时性好 | 要求调用方暴露可达端点并处理重放、重试、鉴权；两侧服务部署位置不对称，联调成本高于收益 |
| **消息队列 + 消费端** | 天然解耦、可水平扩展 | 引入中间件依赖与运维负担，超出当前规模所需；异步任务的语义已被上述 API 形状覆盖 |

## Consequences

**正面**

- 提交与执行解耦：客户端可以在任意时刻断开、重连、换进程查询。
- 可观测：任何时刻都能读到任务处于哪个阶段、已产出哪些中间产物。
- 为后续重试、取消、超时治理留出了统一的挂载点。

**代价**

- **必须实现任务存储与查询**：需要持久化 job 记录，并保证状态迁移的原子性。
- **调用方必须轮询**：客户端要么轮询，要么自行封装等待逻辑。
- **引入了状态一致性要求**：状态枚举成为契约的一部分，改枚举即破坏兼容（见 `contracts/error-codes.md`）。
