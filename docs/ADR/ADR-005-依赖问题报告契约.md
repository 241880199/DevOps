# ADR-005：依赖问题报告的字段与来源标记

- **状态**：已采纳
- **日期**：2026-09-20

## Context

检测服务检出依赖问题后，需要把结果交给修复服务。这份报告是**跨服务、跨团队的**：产报告的一方和用报告的一方不是同一批人，中间还夹着人工构造的参考答案。

报告的内容设计上有三个真实约束：

1. **光有 (target, dependency) 无法复核。** `main.o 缺 config.h` 这条信息本身没法验证——复核者需要知道这条声明写在哪一行、判定依据是什么。缺了这两样，报告只能被无条件相信，或者被无条件怀疑。

2. **人工构造的参考答案必须能被区分出来。** 基线样本里有相当一部分是人工标注的「标准答案」。如果人工答案和工具检出混在一起、且靠解析检测器名称字符串来分辨，那么统计工具准确率时必然把人工答案算进去，指标会虚高。这类错误不会报错，只会让结论悄悄失真。

3. **同一份报告里可能同时有两类发现。** 一次检测往往同时报出缺失依赖和冗余依赖。而下游的修复服务只修其中一类。

## Decision

报告结构由 `contracts/error-report.schema.json` 定义，以 artifact URI 引用交接。四条具体决定：

**1. 每条发现必须同时带 `location` 与 `evidence`，二者均为必填。**

```json
"location": { "file": "Makefile", "line": 7, "detail": "main.o 的依赖列表只声明了 main.c" },
"evidence": { "kind": "FILE_ACCESS", "detail": "main.o 构建期间读取了 config.h" }
```

`location` 回答「改哪里」，`evidence` 回答「凭什么这么说」。缺任一者，报告不可复核。

**2. 来源类别用独立的 `provenance` 枚举显式表达，不靠解析 `detector` 字符串。**

```json
"detector": "BuildChecker",
"provenance": "TOOL"
```

`detector` 说明**是哪个工具**，`provenance` 说明**是哪一类来源**（`TOOL` / `INSTRUCTOR_ORACLE` / `MANUAL`）。两者职责不同。消费方过滤人工样本时只需判断枚举值，无需猜测字符串命名约定。

**3. 报告整体可含两类发现，但修复请求把范围限定为 `MISSING`。**

报告如实反映检测结果，不做裁剪；`job-input-repair.schema.json` 中的 `report.finding_type` 固定为 `MISSING`，请求修复冗余依赖会被拒绝。

**4. `commit` 在报告与每条发现上都出现。**

报告级 `commit` 说明整份报告的依据版本；发现级 `commit` 允许单条发现溯源到它成立时的提交，用于增量检测的场景。

## Alternatives

| 方案 | 优点 | 为何不选 |
| --- | --- | --- |
| **只用 `(target, dependency)`** | 结构最小 | 无法复核。复核者不知道去哪一行确认，也不知道判定依据，只能选择相信或不信 |
| **用 `detector` 字符串区分人工与工具** | 少一个字段 | 依赖字符串命名约定，脆弱且隐式。新增检测器时若命名不合约定就会静默算错，而错误不可见 |
| **把报告内嵌进任务响应** | 一次拿到全部 | 报告规模可达数 MB，会让任务响应体膨胀；与 ADR-002 的产物交接约定冲突 |
| **报告只含 MISSING，冗余依赖另出报告** | 下游无需过滤 | 检测一次要产出两份报告，且丢失「同一配置下两类问题并存」的整体视图 |

## Consequences

**正面**

- 报告可被独立复核，争议时可回溯。
- 人工标注与工具产出可被机械区分，工具准确率统计不会被人工答案污染。
- 修复服务的输入边界明确，不会误修冗余依赖。

**代价**

- **报告体积增大**：每条发现多了两个必填对象。对上千条发现的报告，这是可观的增长。
- **`provenance` 需要产出方正确填写**。填错不会被 schema 拦住——schema 只能校验取值合法，无法校验取值属实。
- **要求检测方产出证据**：不是所有检测手段都能给出同等强度的证据，弱证据只能以较低 `kind` 记录。
