# ADR-004：结果仅在终态交付，执行中不返回部分输出

- **状态**：已采纳
- **日期**：2026-09-20

## Context

任务采用异步模型（见 ADR-001），执行期间调用方会反复轮询 `GET /v1/jobs/{job_id}`。于是产生一个问题：**执行中的任务要不要返回已经产生的部分结果？**

环境生成任务在执行过程中确实会不断累积中间产物：第 0 轮的候选 Dockerfile、每轮的构建日志、已定位到的错误、已尝试的补丁。把这些通过 `output` 回传，调用方在任务结束前就能看到进展。

但这会引入第二种输出形状。`output` 的结构由 `job-output-draft.schema.json` 定义，其中 `result.build_ok` / `verify_ok` / `rounds_used` 等字段只有在任务结束时才有确定取值。若允许 `RUNNING` 携带部分 `output`：

- 消费方必须同时处理「部分输出」与「完整输出」两种结构，且要自行判断哪些字段此刻有意义；
- `result`、`iterations` 的必填性随 `status` 浮动，schema 无法用静态约束表达，只能退化为文档约定；
- 消费方若误把部分结果当作最终结果使用，会拿到一个尚未验证的镜像引用。

## Decision

**`output` 与 `error` 只在终态出现。**

- `QUEUED` / `RUNNING`：只返回任务元数据（`job_id`、`status`、`execution`、`input` 回显）。
- `SUCCEEDED`：返回完整 `output`，符合 `job-output-draft.schema.json`。
- `FAILED` / `TIMED_OUT` / `CANCELLED`：返回 `error`。

该约束由 `task.schema.json` 的 `allOf` 强制，并由 `scripts/validate.py` 检查 04 验证——向 `QUEUED` / `RUNNING` 的任务注入 `output` 或 `error` 都必须被拒绝。

于是 `status` 成为判断「结果是否可用」的**唯一**依据，消费方只需一条分支。

## Alternatives

| 方案 | 优点 | 为何不选 |
| --- | --- | --- |
| **执行中返回部分 `output`** | 进展可见，长任务体验好 | 引入第二种输出形状；字段必填性随状态浮动，schema 无法静态约束；消费方可能误用未验证的中间结果 |
| **执行中返回部分 `output`，但另设 `partial: true` 标记** | 显式区分两种形状 | 消费方仍需处理两种结构，只是多了一个开关；未解决必填性浮动的问题 |
| **新增独立的进展查询接口**（如 `GET /v1/jobs/{id}/progress`） | 形状分离干净，进展仍可见 | 增加一个端点与一套结构，当前需求强度不足以支撑。若将来确有必要，这是首选扩展路径 |
| **用 `execution` 字段承载进展信息** | 不新增结构 | `execution` 的定位是时间戳与尝试次数，塞入业务进展会使其语义混乱 |

## Consequences

**正面**

- 消费方只面对一种输出形状，`status` 是唯一判据，分支逻辑最简单。
- schema 可以用静态约束表达「终态才有结果」，无需依赖文档约定。
- 不会出现「消费方误用未验证的中间产物」这类事故。

**代价**

- **长任务执行期间不可观测。** 轮询只能看到 `QUEUED` / `RUNNING` 与开始时间，看不到跑到第几轮。排查卡住的任务需要查服务端日志。
- 若将来确需进展可见，需要新增独立端点（见备选方案），属于兼容性新增，不会破坏现有契约。
