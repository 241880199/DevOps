# ADR-007：DRAFT 输出回报 `configuration_id`

- **状态**：**已被 `docs/ADR/ADR-011` 取代**（2026-09-24）。环境身份改由 `environment_id` 承载，本提案中的 `configuration_id` 不再作为当前字段定义；原文保留为交换历史，不改写。
- **日期**：2026-09-20
- **相关契约**：`contracts/job-output-draft.schema.json`、`contracts/job-input-full-check.schema.json`

## Context

全量检测的输入要求两个字段共同确定基线身份：

```json
"environment": {
  "image_ref": "draft-fixture-ok:1.0",
  "configuration_id": "cc-MODE0"
}
```

理由是充分的，已写入 `contracts/job-input-full-check.schema.json`：同一提交在不同构建配置下依赖关系不同，缺了配置标识，两份依赖图就不可比。

问题在于**这个标识没有生产者**。检查四类服务的输出：

| 服务 | 是否产出 `configuration_id` |
| --- | --- |
| DRAFT（环境生成） | **否**（本次改动前） |
| FULL_CHECK / INCREMENTAL_CHECK | 否，它们**消费**它 |
| REPAIR | 否 |

也就是说，检测方要在输入里填一个没人产出的值，只能自己发明；而环境事实上是 DRAFT 造的。结果有两种，都不好：

1. 检测方按自己的理解命名（`cc-MODE0`、`mode0`、`MODE=0`），同一个环境在平台里出现多个名字，跨任务的基线比较静默失效；
2. 检测方干脆不区分配置，把不同配置下的依赖图混在一起比较——这正是该字段要防的事。

这一点在 `docs/backlog.md` 里挂了两轮，标注为「需明确由谁产生、语义为何」。

## Decision

**由 DRAFT 在输出中回报 `configuration_id`，作为可选字段。**

```json
"output": {
  "image_ref": "draft-fixture-ok:1.0",
  "resolved_commit": "b06e66ec…",
  "configuration_id": "cc-MODE0",
  ...
}
```

- **语义**：本次生成的构建环境所**固定**下来的配置标识——基础镜像、工具链版本、传给构建命令的选项，凡影响依赖关系的都算在内。
- **产生方**：DRAFT。它是环境的产出方，也是唯一知道环境里到底装了什么、编译选项是什么的一方。
- **消费方式**：检测方在 `environment.configuration_id` 里直接沿用该值，不自行命名。这样「同一个环境」在平台里天然只有一个名字。
- **取值形态**：建议 `cc-<配置摘要>`，摘要由服务端选定并保持稳定。契约只约束它是非空字符串，不约束编码方式——编码方式属于实现，一旦写进契约就改不动了。
- **可选性**：**可选**。不填时检测方需自行约定，行为与本次改动前一致。因此这是兼容变更（新增可选字段，见 `docs/backlog.md` 的「契约变更约定」），依赖检测服务不需要立即配合。

## Alternatives

| 方案 | 优点 | 为何不选 |
| --- | --- | --- |
| **检测方自己命名** | 不动契约 | 就是当前状态。同一环境多个名字，跨任务比较静默失效，且失败不可见 |
| **由平台侧统一分配** | 名字全局一致 | 需要一方知道所有环境的配置，即需要 DRAFT 先上报——绕回本方案，还多一层 |
| **用 `image_ref` 代替** | 不新增字段 | 镜像名不承载配置：同一个镜像可以用不同 `-D` 选项构建出不同依赖图（E3 的 C2 提交正是这个场景）。用它当配置标识会把不同配置误判为同一配置 |
| **设为必填字段** | 强制对齐 | 破坏兼容，需递增 `schema_version`。E2 阶段应先把提案跑通，不宜一次到位 |
| **把配置标识写进 `image_ref`**（如 `draft-fixture-ok:1.0-mode0`） | 不新增字段 | 靠字符串编码传语义，脆弱且隐式；镜像标签的语义由镜像仓库决定，不该被契约征用 |

## Consequences

**正面**

- 平台里「一个环境一个名字」，跨任务、跨提交的基线比较有了共同基准。
- 检测方不再需要发明标识，减少一类静默失配。
- 兼容变更，依赖检测服务可择期跟进，不阻塞当前联调。

**代价**

- **需要 DRAFT 侧实现**：mock 里已置为固定值 `cc-mock0`，真实实现需要按实际配置生成摘要，且要保证同一配置每次得到同一个值——否则标识不稳定，比较照样失效。这条约束写在字段描述里，但 schema 无法校验。
- **配置摘要的粒度需要双方认可**：粒度太粗（只看基础镜像）会漏掉 `-D` 选项这类差异；太细（含时间戳、容器 ID）则每次构建都得到新值，等于没有标识。本 ADR 给出的判据是「凡影响依赖关系的都算在内」，具体到实现仍需 A、B 双方在 E3 前对齐一次。
