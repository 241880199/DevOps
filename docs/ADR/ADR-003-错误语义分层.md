# ADR-003：错误语义分层——「发现问题」与「执行失败」分开表示

- **状态**：已采纳
- **日期**：2026-09-20

## Context

平台上有一类服务（依赖检测、依赖修复）的**正常职责就是报告问题**：检出缺失依赖、检出冗余依赖、发现某个修复候选无效。

于是出现一个语义陷阱：任务「跑成功了」和任务「没发现问题」，是两件完全不同的事，但在朴素的实现里很容易被合并成一个 `success: false`。

这种混淆会引发连锁故障：

- 下游调度器把一次**成功的分析**误判为基础设施故障，触发重试——而重试会再跑一遍昂贵的全量构建；
- 告警系统因正常的依赖发现而被刷屏，真实故障被淹没；
- 流水线因为「发现了问题」而中止，问题报告反而阻断了修复流程。

同时，另有一类货真价实的失败必须显式暴露：镜像构建不出来、任务超时、分析器自身崩溃。这两类信息如果共用同一个字段，消费方就无法区分。

## Decision

**把两类结果分别放在两个互斥的位置，并使其互相排斥。**

| | 系统执行错误 | 正常分析发现 |
| --- | --- | --- |
| **存放位置** | `job.error` | `output` 及其引用的报告产物 |
| **任务终态** | `FAILED` / `TIMED_OUT` / `CANCELLED` | **仍是 `SUCCEEDED`** |
| **示例** | 镜像构建失败、任务超时、分析器崩溃 | 检出缺失依赖、检出冗余依赖 |

具体约束：

1. **`SUCCEEDED` 必填 `output`，且不得同时携带 `error`**——成功与失败语义互斥，由 schema 强制。
2. **`FAILED` / `TIMED_OUT` / `CANCELLED` 必填 `error`**，`error.code` 采用 `<阶段>_<四位数字>` 分段编码。
3. **迭代过程中的失败不是任务失败**。对 DRAFT 而言，某一轮候选 Dockerfile 构建失败但已定位原因、继续迭代，属于过程状态，记入 `output.iterations[].outcome`，**不写入 `job.error`**。
4. 错误码按阶段分段（3xxx 环境 / 4xxx 执行 / 5xxx 分析），新增时同步更新 `contracts/error-codes.md` 与 schema 约束。

## Alternatives

| 方案 | 优点 | 为何不选 |
| --- | --- | --- |
| **单一 `success: bool` + `message`** | 最简单 | 无法区分「成功且有问题」与「失败」；下游必然误判，正是本 ADR 要解决的问题 |
| **`error` 字段兼作发现列表** | 字段数少 | 语义污染：消费方无法判断该重试还是该处理发现；且成功任务带有 `error` 会使状态机失去意义 |
| **用 HTTP 状态码表达** | 无需额外字段 | 异步模型下创建请求返回 `202` 时结果尚未产生，状态码表达的是**受理结果**而非**执行结果**；且状态码不足以承载错误分类 |
| **全部塞进 `output`，不设 `error`** | 结构统一 | 基础设施故障会伪装成正常产出，超时与崩溃无法被监控系统捕获 |

## Consequences

**正面**

- 「发现问题」不再阻断流水线，也不再污染告警。
- 基础设施故障可以从任务列表里被直接筛出并统计。
- 状态机的终态具有确定含义，重试策略有明确判据。

**代价**

- 消费方需要同时看 `status`、`output`、`error` 三处才能得到完整结论，比看一个布尔值复杂。这一点通过 `contracts/error-codes.md` 的「自检两问」来约束。
- schema 需要条件约束（`allOf` + `if/then`），比扁平结构更难手写；因此把校验固化进了 `scripts/validate.py`。
