# 变更说明：Job 契约 1.0 → 2.0

面向**对接本服务的一方**（依赖检测、调度方、维护者）。一句话概括：**环境成为独立对象，任务只按
`environment_id` 引用它**；四类任务统一 `schema_version=2.0`。

设计理由、备选方案与代价见 `docs/ADR/ADR-011`；字段级语义见 `docs/接口说明.md`。

---

## 1. 字段对照

| 1.0（旧） | 2.0（新） | 说明 |
| --- | --- | --- |
| `configuration_id`（仅 DRAFT 输出） | `environment_id` | 环境身份由环境生成服务产出，平台全局唯一；完整定义经 `GET /v1/environments/{environment_id}` 取 |
| `image_ref`（裸镜像 tag） | `image_artifact_id` | 指向一条 `IMAGE_REF` 产物；镜像信息只有一处定义 |
| REPAIR 输入内嵌 `environment{image_ref, build_command, verify_command, recheck_command}` | `environment_id` + `verification{verify_command, recheck_command}` | 构建方式只在环境里表达；**验证与复检不是构建**，仍由任务给出 |
| REPAIR 输入 `project_subdir` | 用环境的 `project_root` | 报告与 `makefile_path` 的路径基准改取环境；同一个「项目根」只保留一处定义 |
| `report.artifact_uri`（必填） | `report.artifact_id`（必填）+ `artifact_uri`（可选对照） | 取回一律走 `GET /v1/artifacts/{artifact_id}` |
| DRAFT 输入 `repository.commit` 可缩写、可缺省 | 不变（仍是 7–40 位或省略） | 但生成方**必须**解析成完整 SHA 并确认提交真实存在后才写进产物 |
| REPAIR 输入 `repository.commit` / `report.commit` | **必须完整 40 位** | 两者要逐字符比对，缩写会让「同一版本」变成模糊判断 |
| `verification.recheck_command` 可选 | **必填** | `recheck_ok` 是「补丁是否真的消除依赖问题」的唯一依据 |

**新增字段**：DRAFT 输入可选 `runtime_capabilities`（v1 只有 `ptrace`）——能力需求由调用方提出，环境生成
服务据此固定进环境记录；检测类任务引用的环境必须声明 `ptrace`，否则请求被拒。

**产物归属**：环境生成服务自己的产物（`DOCKERFILE` / `BUILD_LOG` / `VERIFY_LOG` / `IMAGE_REF`）
`environment_id` 一律为 `null`（产出时环境尚不存在）；其余服务的产物必须记录所属环境。

---

## 2. 新增接口

| 操作 | 端点 |
| --- | --- |
| 查询环境定义 | `GET /v1/environments/{environment_id}` |

返回体即 `Environment` 对象：`environment_id`、`image`（`IMAGE_REF` 产物编号）、`project_root`（容器内位置）、
`working_directory`、`build_command`、`runtime_capabilities`。**环境创建后不可变**——需要改动就新建一个
（`env-001` → `env-002`），否则下游手里的同一个 ID 会指向两种环境。

---

## 3. 行为收紧（以前照跑、现在被拒）

| 输入 | 结果 |
| --- | --- |
| 引用未登记（或不存在）的环境 | `400` / 查询时 `404` |
| 检测任务引用未声明 `ptrace` 的环境 | `400` |
| 环境生成请求的 `commit` 解析不出仓库中真实存在的提交 | `400`（受理阶段） |
| `project_subdir` / `makefile_path` 是绝对路径、含 `..` 或空路径段 | `400` |
| 修复报告：编号取不到、不是 `ERROR_REPORT`、属于别的环境、内容不合契约、与记录不一致、没有 `MISSING` 发现 | `400` |
| 修复请求声明了 `report.commit` 但与 `repository.commit` 不符 | `400`；未声明时在执行阶段以 `FAILED / REPAIR_6001` 收场 |

**自写联调脚本若走「用 mock 建环境再跑检测」这条路**：生成环境时请声明 `runtime_capabilities: ["ptrace"]`。

---

## 4. 对接方需要做什么

1. 请求体里把 `configuration_id` 换成 `environment_id`，并去掉内嵌的 `environment` 段与 `project_subdir`；
2. `commit` 一律传**完整 40 位** SHA（环境生成请求除外，它接受缩写并由生成方解析）；
3. 修复请求补上 `verification.recheck_command`；
4. 报告引用改为 `artifact_id`（`artifact_uri` 可选，填了必须与产物记录一致）；
5. 环境定义改为按 ID 查询，不要在本地缓存副本——环境不可变，新建会产生新 ID。

---

## 5. 验证方式

```bash
python -m pip install -r requirements.txt
python scripts/validate.py        # 退出码 0 表示全部通过
```

校验覆盖跨样例一致性、环境交接、产物摘要与实物一致、文档示例与契约一致等 273 项；
另可用 `python scripts/mock_server.py` 起 mock 跑通四类任务与环境查询。**注意**：mock 用本仓库的 git
对象解析提交，因此需要一份**带完整历史**的检出（浅克隆或源码包会让校验失败、并让带固定 `commit`
的环境生成请求被拒）。
